# 15. 增量修改与版本回滚详细设计

> 配套：`08` §5.2 接口契约、§5.6 回滚契约；`07` 第 136 行上下文拼装原则；`06` ADR-04。
> 本文解决一个问题：**用户说"把得分改成必填"，系统凭什么只改这一处，而不是把整个应用重生成一遍。**

| 项 | 内容 |
|---|---|
| 版本 | v1.0 |
| 状态 | 已实现（chat / versions / rollback 三个接口 + 前端对话条） |
| 依赖 | AppSpec zod 定义（`src/lib/spec/schema.ts`）、引用完整性校验（`src/lib/spec/validate.ts`） |

---

## 1. 目标与非目标

**目标**

1. 一条自然语言指令 → 一组 JSON Patch（RFC 6902 子集）→ 新版本快照。
2. 补丁只能落在白名单路径内，越界整条丢弃并告知。
3. apply 后必须重新通过结构校验与引用完整性校验，不通过则**不产生新版本**。
4. 回滚不删除历史，把旧 spec 复制成新版本，因此"回滚本身也可回滚"。

**非目标**

- 不做多人同时编辑同一应用（无乐观锁，后写覆盖）。
- 不做 patch 的可视化 diff 编辑器（只在 UI 展示"应用了 N 处"）。
- 不支持任意 JSON Patch：只支持 `add / replace / remove / move` 四个操作。

---

## 2. 为什么是 Patch 而不是重生成

| 维度 | 重生成（整份 spec 重出） | JSON Patch |
|---|---|---|
| 用户已有数据 | 字段 key 可能变，旧数据成孤儿 | 不动未涉及的字段，数据天然兼容 |
| 可解释性 | "我只要改标题，怎么页面全变了" | 只改目标节点，diff 可读 |
| 失败成本 | 一次失败整份作废 | 单条补丁可丢弃，其余照用 |
| 成本 | 输出 2–3k tokens | 输出 100–300 tokens |

代价：模型必须知道现有 spec 的**精确路径**，否则路径写错。所以上下文里必须带当前 spec 全文（见第 6 节），并且路径不存在时**丢弃该条而不是整页重生**。

---

## 3. 路径白名单

只允许改这四棵子树，其余一律拒绝（`422 PATCH_OUT_OF_SCOPE`）：

```
/app/(name|theme|description|icon)
/entities/{i}(/fields(/{j})?)?
/pages/{i}(/(columns|filters|cards)/{j|-) )?
/sharePolicy(/mode)?
```

硬规则：

| 规则 | 说明 |
|---|---|
| 根节点白名单 | 首段必须是 `app` / `entities` / `pages` / `sharePolicy`；`/specVersion` 不可改（版本协议不能被用户指令改写） |
| 段数上限 | ≤ 6 段，防止构造超深路径 |
| 危险键 | `__proto__` / `constructor` / `prototype` 一律拒绝（原型污染） |
| 指针转义 | 按 RFC 6901 处理 `~1` → `/`、`~0` → `~` |

---

## 4. apply 语义

伪代码（实现见 `src/lib/patch.ts`）：

```
for op of patch:
  if not isAllowedPath(op.path): dropped.push({path, reason:'OUT_OF_SCOPE'}); continue
  parent = resolveParent(spec, op.path)
  if parent 不存在:            dropped.push({path, reason:'PATH_NOT_FOUND'}); continue
  switch op.op:
    replace: 对象父节点 → 已存在则赋值；不存在且属性名在 KNOWN_PROPERTIES 白名单内则写入（受控 upsert）
             数组父节点 → 下标必须存在
    remove:  必须已存在 → 数组 splice / 对象 delete
    add:     数组允许 index === length 或 '-'（追加）；对象允许新键
    move:    from 必须允许且存在 → 先删后加
    default: dropped.push({reason:'UNSUPPORTED_OP'})
```

> **为什么 replace 允许受控 upsert**：`required`、`enum`、`format` 这类属性在 AppSpec 里可选，初始可能根本不存在键。若严格按 RFC 6902「replace 目标必须存在」，则"把勘误说明改成必填"这类完全合法的指令会被静默丢弃。折中：只允许写入 `KNOWN_PROPERTIES` 里的属性名（约 30 个），路径写错仍然拒绝。

**丢弃不中断**：一条补丁路径写错，不影响其余补丁生效。全部丢完（`appliedOps === 0`）时返回 `degraded: true`，由前端提示用户换个说法。

## 5. 校验链与事务边界

顺序不可交换：

```
1. 指令非空、长度 ≤ 500
2. 生成 patch（模型）
3. 逐条过白名单 + 路径存在性（丢弃制）
4. apply 到当前 spec 的深拷贝上
5. zod 结构校验（specSchema.safeParse）      → 失败 422 SPEC_INVALID
6. 引用完整性校验（validateSpec）             → 失败 422 SPEC_INVALID
7. 事务内：insert app_versions(version+1, spec, patch) + update apps.currentVersion
```

第 5、6 步任一失败：**不写库**，把问题单回给用户（前端展示"这次修改会导致 X 页引用了不存在的字段，已放弃"）。这比"改坏了让人自己回滚"体验好一个量级。

## 6. 上下文拼装（为什么必须带全量 spec）

| 内容 | 是否带 | 理由 |
|---|---|---|
| 当前 spec 全文 | **带** | patch 的 path 精确依赖它；裁掉会让模型瞎猜字段序号 |
| 最近 3 条 patch 的一句话摘要 | 带 | 让模型知道"上一轮改了什么"，避免重复应用已撤销的变更 |
| 完整历史 patch | 不带 | 每轮多 1–2k tokens，且可能互相回滚（A→B→A），反而误导 |

模型输出契约：

```json
{ "patch": [ { "op": "replace", "path": "/entities/0/fields/4/required", "value": true } ] }
```

不允许输出解释文字；解析失败回灌一次（把解析错误作为反馈），仍失败则 `422 PARSE_FAILED`。

## 7. 两个通道

| 通道 | 触发 | 行为 |
|---|---|---|
| `mock`（默认） | `LLM_PROVIDER=mock` | 规则匹配意图，产出确定性 patch，无需 API key |
| `openai`（真实） | `LLM_PROVIDER=openai` + key | 提示词内联 spec 与路径白名单，要求只输出 JSON |

mock 通道的意图规则（`src/lib/agent/patchAgent.ts`）：

| 指令特征 | 产出的 patch |
|---|---|
| 含"必填" + 某字段名 | `replace /entities/{i}/fields/{j}/required = true` |
| "加/新增 … 字段「X」" | `add /entities/{i}/fields/-`（按 X 猜类型，默认 text） |
| "列表/表格里加 … 列" | `add /pages/{table}/columns/-` |
| "加 … 卡片/指标"（含平均/合计） | `add /pages/{stats}/cards/-`（fn 取 avg/sum/count） |
| "删/去掉 … 卡片" | `remove /pages/{stats}/cards/{j}` |
| "改名/改成 X" | `replace /app/name` |
| "暖色/冷色/中性" | `replace /app/theme` |
| 都不匹配 | 空 patch → `degraded: true` |

mock 的意义不是"假装有模型"，而是**在没有 key 的情况下也能把链路完整演示一遍**，并且它的输出同样要过白名单与校验——这一点不能省。

---

## 8. 版本与回滚

- 版本号单调递增，`app_versions(app_id, version)` 唯一。
- 回滚 = **读旧快照 → 写成新版本** → 更新 `apps.currentVersion`。历史一行不删。
- 因此"回滚到 v2"之后当前是 v4（内容是 v2 的），再回滚到 v3 依然可行。
- 数据不随 spec 迁移：旧字段值仍留在 `app_records.payload` 里，只是新 spec 不展示。所以"改结构不丢数据"可以现场验证。

回滚的错误语义：目标版本不存在或不属于该应用 → `404`；当前版本已等于目标内容 → `409 CONFLICT`。

## 9. 验收用例

| ID | 操作 | 判定 |
|---|---|---|
| P-01 | 对巡检应用说"把巡检得分改成必填" | 返回 v2，patch 只有 1 条 replace；表单上得分显示 * |
| P-02 | 已有一条记录后执行 P-01 | 记录仍在列表里，列表页字段不变 |
| P-03 | 说"加一个字段：整改负责人" | v3；表单末尾出现新字段；旧记录该字段为空显示 — |
| P-04 | 说"列表里加上区域列" | v4；列表多一列，值来自旧记录 payload |
| P-05 | 构造 `replace /specVersion` 的越界 patch | 该条被丢弃，返回 warn，其余补丁生效 |
| P-06 | 构造会让 stats 引用不存在字段的 patch | `422 SPEC_INVALID`，**不产生新版本** |
| P-07 | 回滚到 v1 | 当前变成新版本号，内容为 v1；历史版本仍可见 |
| P-08 | 连续两次回滚到同一版本 | 第二次 `409 CONFLICT` |
| P-09 | 说一句完全听不懂的话 | `degraded: true`，不产生新版本 |
