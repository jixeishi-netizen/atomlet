# Atomlet（小原子）风险登记册与应对

版本：v1.0　编制：苏小测　适用窗口：提交前 48 小时
使用方式：**提交前每 2 小时过一遍第 5 节的评审节奏；演示当天只执行第 7 节的降级剧本，不再临时改代码。**

---

## 1. 这份登记册解决什么问题

48 小时交付的最大威胁不是"功能少"，而是"演示那一刻不可用"。功能少可以讲取舍，不可用没有第二句话可说。所以本册不记录"可能写不完"这类无用风险，只记录**会在演示现场被看见**、且**有具体动作可做**的风险。

每条风险都必须落到一个可执行的东西上：不是"注意稳定性"，而是"准备 3 个已生成好的应用作为降级入口"。凡是给不出兜底方案的条目，直接删掉，不留在册子里充数。

## 2. 评级口径

| 维度 | 高 | 中 | 低 |
|---|---|---|---|
| 概率 | 大概率会遇到，或已经出现过一次 | 有明确触发条件，但不必然发生 | 需要叠加多个巧合 |
| 影响 | 演示中断 / 数据错误 / 信任崩塌 | 演示可绕行，但观感或可信度受损 | 只有自己知道，观众无感 |
| 等级 | 高×高、高×中、中×高 | 其余组合 | 低×低、低×中 |

等级为"高"的条目必须在功能冻结前处理完或备好兜底资产；"中"必须在演示前确认兜底可用；"低"仅记录。

## 4. Top3 风险展开

### Top1 R-04 结构化输出不稳定 —— 生成链路的单点故障

**原因。** 三阶段链路里，Builder 的输出必须严格符合 AppSpec schema，但模型天然倾向于"多说两句"：给 JSON 包一层解释、用 markdown 围栏、字段名自创、枚举值写出 schema 之外的值。Critic 能发现一部分，但 Critic 本身也是模型，它也会误判。这个风险的可怕之处是它**不均匀**——同一段 prompt 连续 5 次成功，第 6 次失败，于是人会产生"已经好了"的错觉。

**影响。** 生成失败是演示的第一个动作。第一个动作失败，后面五个功能再漂亮也没有展示机会。而且失败形态通常很难看：页面停在 40% 的进度条、或者抛出一段没人看得懂的 JSON parse error。

**具体动作。**
1. 所有模型输出先过一遍容错解析器：剥围栏、截取首个 `{` 到末个 `}`、去掉尾逗号，再交给 zod。
2. zod 报错信息结构化后回灌给模型，明确写出"字段 `pages[0].fields[2].type` 不在允许值内，允许值是 form/table/detail/stats/board/chart"，最多重试 3 次。
3. 每次生成都把原始输出和校验结果落盘到 `logs/gen/`，任何一个失败样本都能在 5 分钟内复现。
4. 前端准备一个"用示例应用继续"的按钮：生成失败时点击直接载入预生成 AppSpec，演示可无缝继续往下讲。

### Top2 R-10 生成质量不稳定 —— 让人不敢相信这是"能用的系统"

**原因。** 即使 JSON 完全合法，生成结果也可能难看：字段顺序乱、表单一行塞八个输入框、配色像一个 2009 年的后台、统计页只有一个孤零零的数字。原因是我们把设计决策交给了模型，而模型没有稳定审美。

**影响。** 面试方判断"能不能用"的第一层其实是"看起来像不像个正经东西"。质量翻车不会让人说"生成失败"，而是让人心里默默降级成"玩具"。这种损失比报错更难挽回，因为没有错误信息可以指给你看。

**具体动作。**
1. 把设计决策从模型手里拿走：统一设计令牌（间距、字号、圆角、颜色）与六种组件的固定布局模板，模型只输出结构。
2. prompt 里放 2 个 few-shot，都是同一个应用的"好版本"，让模型对齐字段命名与描述风格。
3. 演示只用 3 个已经调好的场景（客户线索、设备巡检、招聘看板），现场生成作为"过程演示"，不作为"结果演示"。
4. 准备一段 90 秒录屏：这三个场景在理想状态下的完整操作，作为"平时跑起来是这样"的客观证据。

### Top3 R-13 在线链接失效 —— 交付物本身打不开

**原因。** 免费部署实例会休眠，免费数据库有连接数上限，构建缓存会过期，域名解析偶尔抽风。这些都不在我们控制范围内，但只要发生一次，收到的就是"链接打不开"这五个字。

**影响。** 题目明确要求"在线访问链接"。链接打不开等于交付物缺失，后面所有解释都是减分项。这是唯一一个"技术全对也会失败"的风险。

**具体动作。**
1. 主备两个部署地址，部署到不同平台，都指向同一份代码但各自独立数据库；备地址只做只读演示，数据预置。
2. 演示前 15 分钟跑冒烟清单第 1 条，失败立刻切备地址，不再排查。
3. 交付邮件里同时给出主地址、备地址、以及"如均不可访问，请看我附的录屏"。
4. 本地 dev 环境保持可一键启动（`pnpm demo:seed` 灌种子数据），作为最后一道。

## 5. 风险评审节奏

| 时点 | 复查对象 | 要回答的问题 | 输出 |
|---|---|---|---|
| T+2h（首次可运行） | R-01、R-04 | 是否已有一条稳定成功的 happy path？失败率大概多少？ | 通过率记录，决定是否需要提前启用示例应用兜底 |
| T+4h（主流程跑通） | R-02、R-06、R-08 | 线上部署是否已通？SSE 在线上是否逐帧？连接数是否吃紧？ | 部署验证结论，SSE 是否切轮询 |
| T+6h（功能冻结） | 全表 16 条 | 哪些风险已消失？哪些等级需要上调？兜底资产齐了吗？ | 遗留风险清单（只留无法消除的），移交演示脚本 |
| 演示前 30 分钟 | R-03、R-13、R-14 | 网络、主备地址、手机端是否都验过？ | 冒烟结果，决定是否启用降级剧本 |
| 演示后 1 小时 | 实际发生过的条目 | 哪条真的发生了？兜底是否有效？ | 复盘记录，写进 README 的"已知问题" |

评审只做一件事：**把等级改对、把兜底确认可用**。不在评审里临时加需求，也不在评审后改架构。

## 6. 兜底资产清单（演示前必须全部到位）

| # | 资产 | 到位标准 |
|---|---|---|
| 1 | 3 个预生成应用（客户线索、设备巡检、招聘看板） | 每个至少 8 条记录；其中一个已开启分享且有 3 条外部填报记录；页面无空态 |
| 2 | 90 秒全流程录屏 | 1080p，含"新建 → 生成 → 填报 → 改需求 → 回滚"完整动作，可离线播放 |
| 3 | 关键页面截图 8 张 | 生成三阶段、六种组件、分享填报、回滚对比，存本地文件夹，命名带序号 |
| 4 | 本地可一键启动环境 | `pnpm dev` + `pnpm demo:seed` 两条命令能还原演示数据，不依赖外网 |
| 5 | 主备线上地址 + 手机热点 | 两个地址都能打开同一个应用；热点已验证可上网 |
| 6 | 一页能力边界与路线图 | A4 单页，列出做完了什么、明确不做什么、下一步三件事 |

少任何一项，都不算"准备好演示"。这六项的准备成本约 40 分钟，是本次投入产出比最高的一段时间。

## 7. 演示当天的降级剧本

原则三条：**先切再解释**（切换动作不超过 20 秒）、**不解释技术细节超过一句话**、**永远保留"我还可以给你看这个"的主动权**。不道歉式开场，也不假装问题不存在。

### 7.1 情形一：打不开（链接 502 / 白屏 / 转圈超过 10 秒）

| 项 | 内容 |
|---|---|
| 判定 | 刷新一次仍打不开，或首屏 10 秒未出现 |
| 第一句话 | "线上这个免费实例有休眠，我先用备用的地址给你看，内容是一样的。" |
| 动作 | 打开备地址；备地址也失败则 `pnpm dev` 起本地，切屏幕共享 |
| 切到哪 | 备地址 → 本地 dev（种子数据已就绪）→ 90 秒录屏 |
| 收尾 | "链接我稍后单独发你，你随时可以自己点。" |

### 7.2 情形二：生成卡住（进度条 60 秒不动，或直接报错）

| 项 | 内容 |
|---|---|
| 判定 | 点击生成后 60 秒内没有进入"构建完成"，或出现错误提示 |
| 第一句话 | "这条链路在模型侧偶发超时，我先切到已经生成好的一个，接着往下讲；生成这部分我最后用录屏补给你看。" |
| 动作 | 点界面上的"用示例应用继续"，或直接打开预生成的客户线索应用；不在现场重试第三次 |
| 切到哪 | 预生成应用（客户线索）→ 继续讲六组件、填报、对话修改、回滚 |
| 收尾 | 演示结束前主动说："生成那段我用录屏补 40 秒，你就能看到完整链路。" |

### 7.3 情形三：生成成功了但结果难看（字段荒谬、排版乱、看着像半成品）

| 项 | 内容 |
|---|---|
| 判定 | 生成结果需要你说出"它有时候会这样"这句话 |
| 第一句话 | "这次字段拆得不太合理，我换个说法再生成一次，你看看差别。" |
| 动作 | 只用同一句需求改写一次（换更具体的字段描述）；若第二次仍难看，立刻切预生成应用，不再迭代 |
| 切到哪 | 预生成应用 → 用"版本回滚"演示两次生成结果的对比 |
| 收尾 | "生成质量对描述很敏感，这也是我把 few-shot 和固定模板加进来的原因。" |

**不使用的说法**（会显著减分）："可能是网络问题"（推责）、"这个功能本来是好的"（无证据）、"时间太紧所以没做完"（自我否定）。要说的永远只有一句：现在切到哪、接下来看什么。

## 8. 风险与测试用例的对应

风险清单不是孤立的，本册每条高等级风险都在测试计划里有对应验证动作，避免"登记了但没人验"。

| 风险 | 验证用例 | 验证方式 |
|---|---|---|
| R-01 / R-04 | TC-07、TC-10、TC-11、TC-15 | 正常生成 1 次 + 超时 1 次 + 打桩非法输出 1 次 |
| R-02 / R-13 | 冒烟清单第 1、2 条 | 主备地址各开一次，手机流量一次 |
| R-05 / R-06 | TC-14 | 断网 15s 再恢复，观察是否给出终态与重连提示 |
| R-07 | TC-27 | 250 条记录翻页到第 13 页 |
| R-08 | 集成测试 | 连续 20 次并发请求后查 `pg_stat_activity` 连接数 |
| R-09 | TC-30、TC-31、TC-32、TC-28 | 无 token / 过期 / 只读 / 跨 app 四种越权 |
| R-10 | TC-16、TC-17、TC-20 | 六组件渲染 + 空态 + 长文本，人工判观感 |
| R-14 | TC-34 | iPhone 真机 375px 完成一次填报 |
| R-15 / R-16 | TC-26 | 用合成特殊字符数据，确认无真实个人信息入库 |
