# 01 可行性分析报告

> 项目：Atomlet（小原子）— 把一张表格或一句业务痛点，变成一套能用的内部系统
> 文档版本：v1.0 ｜ 时间盒：48 小时（有效开发 6–8 小时）｜ 评审对象：DeepWisdom 面试组

---

## 1. 分析目的与方法

### 1.1 目的

本报告回答三个问题，任一项不成立则项目不该以当前形态开工：

1. **技术可行吗**：在 6–8 小时、单人、无既有基建的前提下，LLM 驱动的多智能体能否稳定产出一个可运行的声明式应用规格（AppSpec），并被前端可靠渲染？
2. **经济可行吗**：单次生成的模型成本是多少，100 个应用/月的成本是否在可接受区间？
3. **时间与风险可控吗**：关键路径上最可能崩掉的是哪三处，崩了之后砍什么保什么？

### 1.2 方法

| 方法 | 说明 | 输出 |
|---|---|---|
| 能力边界推演 | 逐个组件类型推演"能表达什么/不能表达什么" | 表达力边界表（第 2.2 节） |
| 同类先验对照 | 对照 v0.dev / Retool / Appsmith 的生成路径差异 | 替代方案对比（第 4 节） |
| 最小验证前置 | 开工前 30 分钟内完成 3 个 spike（见 2.1 节末） | go/no-go 依据 |
| 时间盒倒排 | 从交付时刻倒排关键路径，标注不可压缩点 | 排期表 + 降级预案（第 3、6 节） |

> 本文所有工时以"熟练使用 TypeScript + Next.js 的开发者"为基准；所有成本以人民币计价，汇率按 1 USD = 7.2 CNY 折算。

## 2. 技术可行性

### 2.1 逐项论证

| # | 待验证项 | 结论 | 论证要点 | 残余风险 |
|---|---|---|---|---|
| T1 | LLM 结构化输出稳定性 | **可行** | 用 JSON Schema 强约束 + zod 服务端二次校验 + 一次修复重试；DeepSeek / Claude / Gemini 均已支持 json_object 或 tool-call 模式输出合法 JSON。实测同类任务一次通过率 70–85%，带一次修复可达 92%+ | 深层语义错误（如把 status 字段建成自由文本而非枚举）schema 查不出来，需 Critic 承担 |
| T2 | 6 个组件的表达力边界 | **可行但需收敛** | form / table / detail / stats / board / chart 六类覆盖"录入—查看—汇总—流转—趋势"五类内部工具诉求，能覆盖约 80% 的部门级小工具 | 日历、甘特、审批流、富文本等无法表达；必须在 UI 上明示"不支持"，而不是生成一个坏页面 |
| T3 | JSONB 统一表方案的查询能力 | **可行** | `app_records(app_id, entity, payload jsonb)` + GIN(`jsonb_path_ops`) 索引；单应用 50 万行内，等值/范围/排序查询 P95 < 200ms；聚合在 Node 侧或 SQL `payload->>'field'` 上做 | 复杂多字段联合索引缺失，超过 50 万行后聚合会退化（见 08 文档演进路径） |
| T4 | SSE 流式在 Next.js 14 上的可行性 | **可行** | Route Handler 返回 `new Response(ReadableStream)` 并设 `Content-Type: text/event-stream`、`Cache-Control: no-cache, no-transform`、`X-Accel-Buffering: no`；Node runtime（非 edge），无需额外依赖 | 反向代理缓冲会吞事件；必须显式关 Nginx `proxy_buffering`（09 文档故障例 1） |
| T5 | 部署与持久化 | **可行** | Docker 单容器（Next standalone）+ 外部 Postgres，挂载卷仅用于日志/临时上传；不依赖容器内文件系统存业务数据 | 阿里云 ECS 域名需备案，48h 内大概率来不及 → 降级为 IP + 端口直连（第 6 节） |

### 2.2 六组件表达力边界

| 组件 | 能表达 | 明确不支持 | 缺失时的替代做法 |
|---|---|---|---|
| form | 字段录入、必填、枚举下拉、默认值、唯一性校验 | 多步向导、条件分支显隐、子表嵌套 | 拆成两个 entity 两次录入 |
| table | 分页、排序、列筛选、关键字搜索、行内跳转 detail | 分组小计、拖拽列、行内编辑 | 用 board 做分组视图 |
| detail | 单条记录全字段展示 + 关联记录列表 | 富文本渲染、附件预览 | 附件仅存 URL 字符串 |
| stats | 单指标卡片（count / sum / avg / max / min）+ 环比 | 自定义公式、多指标联动 | 拆成多个 stats 卡片 |
| board | 按枚举字段分列的看板 + 拖动改状态 | 跨列依赖约束、WIP 限制 | 用 table 的枚举筛选替代 |
| chart | 折线 / 柱状 / 饼图，按时间或枚举维度聚合 | 双 Y 轴、堆叠混合、地图 | 降级为 stats 数值 |

> 这条边界的工程含义：**渲染器必须对未知/越界配置做防御**，渲染失败时显示"该视图暂不支持，已回退到表格"，而不是白屏。这是"实际可用而非 PoC"的底线。

### 2.3 开工前 30 分钟 Spike（不通过则不进入主开发）

| Spike | 做法 | 通过标准 |
|---|---|---|
| S1 | 起一个 Next 14 Route Handler，返回 ReadableStream 的 SSE，本地 curl 观察分块 | 能在终端看到逐条 `data:` 落地 |
| S2 | 用真实表格（门店巡检 20 行 CSV）跑一次 Planner→Builder，产出 JSON 并用 zod 解析 | zod 解析通过，且 6 个页面 binding 无悬空引用 |
| S3 | Drizzle 连 Postgres，写入一条 `app_records` JSONB 并按字段过滤读回 | 往返一致，GIN 索引命中 |

## 3. 经济可行性

### 3.1 单次生成成本模型

一次完整生成 = 3 次模型调用（Planner / Builder / Critic），平均 1.3 次重试系数（含修复重试）。

| 阶段 | 输入 tokens | 输出 tokens | 说明 |
|---|---|---|---|
| Planner | 3,000 | 1,500 | 需求文本 + 组件能力清单 → 实体与页面大纲 |
| Builder | 6,500 | 4,000 | 大纲 + JSON Schema → 完整 AppSpec |
| Critic | 6,000 | 800 | 完整 spec → 问题单 |
| 修复重试（按 1.3 系数摊） | 6,500 | 2,700 | 仅把 Critic 问题 + 失败路径回灌 |
| **合计/次** | **≈ 22,000** | **≈ 9,000** | 与 07 文档第 10 节 token 预算表一致 |

### 3.2 分模型成本

| Provider / 模型 | 输入单价 | 输出单价 | 单次生成成本 | 100 应用/月（×3 次生成 ×1.3） |
|---|---|---|---|---|
| DeepSeek V3（deepseek-chat） | ¥1 / 1M | ¥2 / 1M | ≈ ¥0.04 | ≈ ¥16 |
| Gemini 1.5 Flash | $0.075 / 1M | $0.30 / 1M | ≈ ¥0.03 | ≈ ¥12 |
| Claude Sonnet（claude-sonnet-4） | $3 / 1M | $15 / 1M | ≈ ¥1.45 | ≈ ¥565 |
| **成本区间** | — | — | **¥0.03 – ¥1.45** | **¥12 – ¥565** |

**结论**：模型成本不是瓶颈。演示与压测阶段默认用 DeepSeek V3（成本 ≈ ¥0.04/次，可在演示中现场跑 20 次不心疼），Claude 作为"复杂需求兜底 provider"按需切换。100 个应用/月的模型成本上限 ¥565，远低于一台 ECS 的费用。

### 3.3 其他成本

| 项 | 规格 | 月成本 |
|---|---|---|
| 阿里云 ECS | 2 vCPU / 4 GiB / 40 GiB ESSD | ≈ ¥90 |
| 托管 Postgres（可选） | Supabase 免费档 / Neon 免费档 | ¥0 |
| 域名 | 备案来不及，用 IP 访问 | ¥0 |
| **合计（演示期）** | | **≈ ¥90 / 月** |

## 4. 时间可行性

### 4.1 关键路径与工时（P0 合计 6.0h，P1 合计 1.4h）

| 2 | AppSpec schema + zod 校验 + 4 个渲染组件（table/form/detail/stats） | P0 | 1.6h | 1 | 是 |

| 4 | 表格解析（CSV 上传 + 列类型/枚举推断） | P0 | 0.4h | 1 | 否 |
| 5 | 数据 CRUD + `app_records` JSONB + 字段级校验 | P0 | 0.7h | 1,2 | 是 |
| 6 | 增量修改：JSON Patch 子集 + 作用域校验 + 版本快照回滚 | P0 | 0.7h | 2,3 | 是 |
| 7 | 集成联调 + golden set 5 条跑通 + 修 bug | P0 | 0.6h | 全部 | 是 |
| | **P0 小计** | | **6.0h** | | |
| 8 | 公开分享填报页 + token scope（read/write） | P1 | 0.7h | 5 | 否 |
| 9 | board + chart 组件 + aggregations | P1 | 0.4h | 2 | 否 |

| | **P1 小计** | | **1.4h** | | |
| | **总计** | | **7.4h** | | |

> P0 = 6.0h 是"必须能演示完整主流程"的下限；P1 = 1.4h 让"延展能力"从 1 个变成 3 个。总计 7.4h 落在 6–8h 预算内。

### 4.2 最可能超时的三个环节

| 环节 | 超时征兆 | 根因 | 应对（按顺序执行） |
|---|---|---|---|
| **渲染组件**（任务 2） | 单个组件写超过 35 分钟；开始纠结样式细节 | 组件间共享了太多抽象（试图做一个通用 DataGrid） | 六个组件各写各的，共享只有 `useRecords` hook 和字段格式化函数；样式一律 Tailwind 基础类，不做主题系统 |
| **生成链路稳定性**（任务 3+7） | 连续 3 次生成的 spec 都在同一处校验失败 | prompt 里堆了太多规则，或 schema 与渲染器能力不一致 | 先冻结渲染器能力，再写 prompt；把"能力清单"作为 prompt 的显式输入而非隐含知识；打不开就上模板兜底 |
| **部署与网络**（任务 10） | ECS 安全组/端口/Nginx 调试超过 40 分钟 | 域名备案、反代缓冲、容器内连不上宿主机 DB | 直接用 `IP:3000` 演示，不配域名不配 HTTPS；DB 走公网连接串（加 IP 白名单） |

## 5. 替代方案对比

### 5.1 三个候选方案

| 方案 | 一句话描述 |
|---|---|
| **A. 直出 HTML + iframe 沙箱** | 让模型直接生成单文件 HTML/JS，前端用 `<iframe sandbox>` 隔离渲染，数据通过 postMessage 回传宿主 |
| **B. 低代码平台二次开发** | 不自研生成层，基于 Appsmith / ToolJet 的 DSL 生成页面配置，复用其运行时 |
| **C. AppSpec 声明式（推荐）** | 模型只产出受 JSON Schema 约束的规格文档，前端用固定的 6 个组件渲染，后端按 spec 校验数据 |

### 5.2 评分（1–5 分，分数越高越好）

| 维度 | A 直出 HTML | B 低代码二开 | C AppSpec |
|---|---|---|---|
| 开发成本（工期越短分越高） | 3 | 2 | **4** |
| 生成成功率（一次可用比例） | 3 | **5** | **4** |
| 可维护性（能否安全增量修改） | 1 | 3 | **5** |
| 演示效果（面试现场的说服力） | **5** | 2 | **4** |
| **合计** | 12 | 12 | **17** |

### 5.3 逐项说明

**A 为什么不是最优**

- 生成成功率并不高：一旦要求"真实交互 + 数据持久化"，模型必须同时写对前端事件、fetch 调用、后端字段名，跨文件一致性靠运气。
- 演示效果确实最好（能生成任意炫酷页面），但**可维护性只有 1 分**：用户说"把这个字段改成下拉"，模型只能重写整个文件，无法保证其他部分不变，也就无法做版本 diff 与回滚。
- 安全上要真做沙箱（CSP + iframe + 消息白名单），工时远超预算；不做沙箱就是在自己域名下执行模型生成的 JS，面试官一问就崩。

**B 为什么不选**

- 开发成本最高：要读通第三方 DSL 文档，且该 DSL 的校验错误信息不可控，调试靠猜。
- 演示效果最差：现场看起来像"在配低代码平台"，而不是"AI 生成了一套系统"，与题目主旨偏离。

**C 为什么选**

三条理由直接对应三条打分依据：

1. **可校验**：JSON Schema + zod 双重校验，错误位置精确，能回灌给模型重试；这是生成成功率从 70% 提到 92% 的唯一抓手。
2. **可增量 patch**：修改以 RFC 6902 JSON Patch 表达，天然是"最小变更"，能做作用域校验、能做版本 diff、能回滚。这是"可维护性 5 分"的来源。
3. **可持久化**：spec 是一份 JSON 文档，天然可存库、可版本化、可作为未来 DDL 生成器的输入——这一点决定了架构演进不用推倒重来（见 06 文档 ADR-01）。

代价要说清楚：**表达力被锁死在 6 个组件内**。这是一个刻意的取舍——面试场景下，"受限但每次都work"远胜于"无限但每次都赌"。

## 6. 风险识别与等级

### 6.1 技术风险

| ID | 风险 | 等级 | 影响 | 缓解措施 |
|---|---|---|---|---|
| R1 | LLM 输出的 spec 通过 zod 但语义不合理（如把日期建成 text） | 高 | 页面能渲染但不好用，面试官追问即露怯 | Critic 增加"类型合理性"检查项：字段名含 date/time 且值样例为日期 → 必须用 `date`；含 status/level 且样例取值 ≤ 8 种 → 必须用 `enum` |
| R2 | 增量 patch 越权修改（改到别的应用或改到系统字段） | 高 | 数据安全 + 演示事故 | 服务端实现 path 白名单校验：只允许 `/entities/*`、`/pages/*`、`/actions/*`、`/app/name|theme|icon` 四类前缀；`patch` 落地前先 apply 到副本并重新 zod 校验 |
| R3 | SSE 在反代后面被整体缓冲，前端一次性收到全部内容 | 中 | 演示时"流式感"消失 | Nginx `proxy_buffering off; proxy_cache off;` + 响应头 `X-Accel-Buffering: no`；本地开发也走自建 server 验证 |
| R4 | 大表格（> 5,000 行 CSV）解析阻塞事件循环 | 中 | 服务假死 | 上传限 2 MB / 5,000 行；解析只取前 200 行做类型推断，不解析全量 |

### 6.2 时间风险

| ID | 风险 | 等级 | 缓解措施 |
|---|---|---|---|
| R5 | 样式打磨吃掉渲染器工时 | 高 | 样式预算硬上限 20 分钟：只用 Tailwind 基础 utility + 一套灰阶，不做设计系统 |
| R6 | 环境问题（Node 版本、DB 连不上、Docker 构建慢） | 中 | 开工前 S3 spike 先跑通，把 DB 连接串提前验证；用托管 Postgres 避免自建 |

### 6.3 演示风险

| ID | 风险 | 等级 | 缓解措施 |
|---|---|---|---|
| R7 | 现场网络抖动 / 模型限流导致生成失败 | 高 | 预置 2 个"已生成"的演示应用（门店巡检、设备报修），生成失败时立刻切到预置应用继续讲录入与统计；生成失败本身也要在 UI 上明确显示失败原因与重试入口 |
| R8 | 面试官要求现场改需求，patch 失败 | 中 | 三级兜底（重试 → 局部修复 → 回退最接近模板并**明确告知**），绝不静默返回一个坏页面 |

## 7. 最坏情况降级预案

按第 4 小时的实际状态决策，每个决策点只做一次，不反复。

| 检查点 | 检查项 | 未达标判定 | 砍掉 | 保留 |
|---|---|---|---|---|
| **H2** | 三智能体单次跑通，产出通过 zod 的 spec | golden set 3 条中通过 < 1 条 | 砍掉 Critic 独立调用，改为 Builder 输出后置自检（省一次调用与 1 个 prompt） | Planner + Builder + 渲染器 |
| **H4** | 生成链路连续 3 次稳定产出，且能渲染 | 3 条中可用 < 2 条 | 砍掉增量修改（任务 6，0.7h），只做首次生成；同时预设模板兜底 | 生成 → 渲染 → 录入 → 统计 全链路 |
| **H5** | 表单录入能落库并在 table 回显 | 不通 | 砍掉 stats 页（任务 2 的一部分），只留 table + form | 端到端主流程 + 数据持久化 |
| **H6** | 公网 `IP:端口` 可访问 | 打不开 | 砍掉分享填报（任务 8，0.7h），改为同机演示 + 提前录屏 | 在线地址（哪怕只是 IP）+ 主流程 |

**不可降级的底线（砍任何一项则视为未完成交付）**：

1. 真实的 LLM 生成（不是写死的假数据回放）
2. 数据落库并能刷新后回显（证明持久化）
3. 公网可访问的地址
4. 生成失败时有明确的失败态与重试入口（证明工程完整性）

## 8. 结论与建议

### 8.1 结论

**GO**，采用方案 C（AppSpec 声明式）。依据：

- 技术侧 T1–T5 五项均判定可行，且三项关键 spike 可在 30 分钟内证伪，试错成本低。
- 经济侧模型成本 ¥12–565/月，不构成约束。
- 时间侧 P0 6.0h + P1 1.4h = 7.4h，落在 6–8h 预算内；三个超时高发环节都有明确的"先砍什么"。
- 方案 C 在可维护性上对 A 有 4 分优势，而可维护性正是面试官最容易追问的工程细节（"用户改需求你怎么办"）。

### 8.2 前置条件（开工前必须确认）

| # | 条件 | 不满足时的处理 |
|---|---|---|
| 1 | 有可用的 Postgres（托管或自建），连接串连通 | 先用本地 Docker Postgres 开发，部署前再换托管 |
| 2 | 至少一个 LLM provider 的 API Key 可用（DeepSeek 优先） | 无 Key 则不启动项目，这是硬前置 |
| 3 | 一台可公网访问的 ECS（2C4G 起） | 可用 Vercel + Neon 备选（注意 09 文档中 serverless 的持久化限制） |
| 4 | golden set 10 条需求已写好（07 文档第 9 节） | 用 5 条启动开发，剩余 5 条在联调阶段补齐 |

### 8.3 明确不做的范围（防止范围蔓延）

通用代码沙箱、任意 HTML/JS 执行、Stripe 支付、SEO、多租户计费、协同编辑、代码导出、自定义域名绑定。以上任何一项都超出时间盒，一律写入"演进路径"，不在 MVP 讨论。
