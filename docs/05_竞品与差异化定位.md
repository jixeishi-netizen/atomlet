## 1 竞品矩阵

| 产品 | 目标用户 | 生成物形态 | 数据持久化 | 增量修改 | 可分享性 | 上手成本 | 定价量级 |
|---|---|---|---|---|---|---|---|
| **Atoms / MGX**（DeepWisdom） | 创业者、独立开发者、想验证想法的人 | 完整可部署的 Web 应用（含前端、后端、账号体系），产物是「一个网站/产品」 | 内置云端存储 + Atoms Cloud，应用自带数据库 | 对话继续，按新需求再生成/编辑；支持可视化编辑器微调 | 产物可部署为公开站点，面向终端消费者 | 中：需要描述产品、理解生成结果、会看部署 | 免费额度 + 订阅制（Beta 期变动频繁） |
| **Lovable** | 会用一点技术的人、独立开发者 | 代码化的全栈应用（React + Supabase），落在用户自己的仓库 | 绑定用户自己的 Supabase 项目，需授权与初始配置 | 对话改代码，改动落在文件级 diff | 一键发布到托管域名，公开可访问 | 中高：需要 GitHub / Supabase 账号 | 免费额度 + Pro 约 $25/月量级 |
| **v0**（Vercel） | 前端工程师、设计师 | UI 组件与页面代码（Next.js / shadcn） | 不自带，需用户自行接后端 | 对话式改组件，偏视觉与交互层 | 通过 Vercel 部署分享 | 中：要有前端基础才用得顺 | 免费额度 + Premium 约 $20/月量级 |
| **Retool** | 企业内部工程师、IT | 内部工具应用（拖拽 + 查询绑定） | 连用户的数据库/API，自己建数据模型 | 手工拖组件、写查询，无自然语言增量 | 站内权限分享，或对外链接 | 高：要会建表、写 SQL、配权限 | 免费小团队 + 约 $10-50/用户/月量级 |
| **飞书多维表格 / Airtable** | 业务人员、运营 | 结构化表格 + 视图 + 自动化，非「应用」 | 产品自带，字段即 schema | 手工加字段、改视图；无对话式修改 | 链接分享 + 权限粒度细 | 低到中：会 Excel 就能上手 | 免费版 + 按席位订阅（约 $20/用户/月量级） |
| **Atomlet（本项目）** | 一线业务人员（门店/区域管理者、行政运营、临时收集者） | 声明式 AppSpec + 运行时渲染出的内部应用（表单/列表/详情/统计/看板/图表） | 统一 `app_records` 表 + JSONB + app_id 隔离，字段级 schema 校验 | 对话生成 JSON Patch，只改目标页面，版本 +1 可回滚 | 分享 token，外部无需账号即可填报；读写模式分离 | 极低：上传一张表或说一句话 | 本 Demo 不涉及商业化 |

### 1.1 逐维度结论

| 维度 | 谁最强 | Atomlet 的位置 | 我们是否要在这一列赢 |
|---|---|---|---|
| 生成物表达力 | Atoms、Lovable | 最弱（只有 6 组件、无自由布局） | 不赢。表达力换不来主流程可用 |
| 数据持久化的真实度 | Retool（接自有库） | 中（统一表 + JSONB，够用但粗糙） | 不赢，但必须「真」（刷新/换设备/外部提交都成立） |
| 增量修改的可判断性 | Atomlet | 最强（spec 级 Patch + diff + 回滚） | **要赢**，这是「生成完还能不能用」的核心 |
| 外部可分享性 | Atomlet | 最强（token + 无账号 + 读写分离） | **要赢**，这是数据回流的唯一入口 |
| 上手成本 | Atomlet | 最低（一张表或一句话） | **要赢**，这决定了目标客群能否成立 |
| 严谨度/可维护性 | Retool | 弱（无审计、无字段级权限） | 不赢，明确写在范围外 |
| 商业化能力 | Atoms | 无 | 不参与，本 Demo 不涉及商业化 |

### 1.2 矩阵的三条读法

1. **横向看「上手中」这一列**：Retool 与 Lovable 的上手成本都压在「你得先有账号/先会建模型」上，而 Atomlet 的目标用户恰好是**没有这些前置条件的人**。这不是功能差异，是用户差异，也是唯一无法被对手快速补齐的差异（他们改产品就要放弃现有客群）。
2. **纵向看「增量修改」与「数据持久化」**：真正决定「生成完还能不能用」的是这两列。Lovable 的改动落在代码 diff，用户要能读懂代码才能判断改对没有；Atomlet 的改动落在 spec diff，用户看「新增一个字段、一个分组」就能判断。可判断性比自由度更重要。
3. **看「可分享性」**：只有 Atomlet 把「外部无账号填报」当作一等能力。Atoms/Lovable 的分享是「把网站发出去给人看」，Atomlet 的分享是「把表单发出去让人写」——一个是展示，一个是采集，后者的数据回流才是本产品的价值闭环。

**取舍**：上表中「要赢」的只有三列，且都不需要新增大模块（Patch、token 分享、一句话入口各占 0.35h/0.20h/0.10h）。反过来，「不赢」的四列中没有一列是 6.5 小时能补上的——这正是把预算投向三列的理由。

## 2 Atoms 能力拆解与取舍

Atoms 的核心资产是**把多智能体编排成一条可交付的软件生产线**。逐项看它解决什么、代价是什么、我们学什么、不学什么。

| Atoms 能力 | 它解决什么 | 代价 / 边界 | Atomlet 的取舍 |
|---|---|---|---|
| 多智能体团队（Iris / Emma / Bob / Alex 等角色分工，覆盖需求、界面、工程、质量） | 把「一个人写不出完整应用」拆成多个可验证的专业步骤，每步产出可检查 | 角色越多，串行链路越长，端到端耗时与失败点同比增加 | **学**：取三阶段（规划/构建/校验）这一最小可行分工。**不学**：不做到 4-6 个角色，因为 60 秒预算撑不住 |
| Race Mode（多方案并行、择优） | 提升单次生成的方案质量，避免「第一版就是最终版」 | 成本与耗时按并行数倍增 | **不学**：生成物是结构化 spec，方案差异主要在字段与页面数量，择优收益低于成本。改为「校验失败回灌重试」 |
| Atoms Cloud（托管后端、数据库、部署） | 让生成的应用真的能存数据、能上线 | 平台绑定；能力边界由平台定义 | **学**：必须有真实持久化与线上 URL，否则 Demo 站不住 |
| 可视化编辑器 | 生成结果不完全可控时，给人一个手工修正的出口 | 编辑器本身是一个独立产品，成本极高 | **不学**：改为「审阅态改字段类型」+「对话打补丁」两个轻量出口 |
| Stripe / SEO 集成 | 让产物具备商业闭环（收钱、被搜到） | 面向创业者场景，与内部工具无关 | **不学**：明确写进范围外，见 02 文档第 8 节 |
| 代码导出 | 让用户接管、二次开发 | 导出即承认「产物是代码」，与声明式路线冲突 | **不学**：AppSpec 就是可导出物，导出的是 spec 不是代码 |

**结论**：Atoms 的取舍逻辑是「为了让生成物达到可商业交付的完整度，愿意付出更长链路和更高成本」。Atomlet 的取舍逻辑相反：「为了让一线人员在 60 秒内拿到能填的东西，愿意牺牲表达力和完整度」。两者对「好」的定义不同，所以不构成替代关系。

### 2.1 Atoms 的能力边界与机会窗口

| Atoms 的边界 | 为什么它不会顺手补上 | 留给 Atomlet 的窗口 |
|---|---|---|
| 面向创业者，产物是「对外发布的产品」 | 客群与叙事绑定在「做能赚钱的产品」上，转向内部工具体系等于换赛道 | 内部工具的验收标准是「能填、能查、能汇总」，与「能赚钱」不冲突也不重叠 |
| 需要一定技术素养才能用好（看部署、看代码、改配置） | 追求表达力必然暴露复杂度，这是产品定位的内在代价 | 零前提下可用：无账号填报、上传即建模 |
| 生成为「一次性重生成」 | Race Mode 与编辑器都建立在「重生成/重编辑」范式上，打补丁范式要重构 spec 层 | spec 级 Patch + 版本回滚 + 数据不丢 |
| 数据模型由生成结果隐式决定 | 隐式模型适合一次性应用，不适合「表结构随业务缓慢演化」 | 显式 AppSpec + 审阅态 + 可人工纠偏字段类型 |

这张表的用法：被问「Atoms 顺手加个功能不就行了」时，答案不是「他们做不了」，而是「他们做这件事要放弃现在的定位」，成本远高于收益。

## 3 差异化定位（三句话）

1. **Atoms 让创业者做出能赚钱的产品，Atomlet 让一线业务人员把手上的 Excel 变成系统。** 前者交付的是一个面向外部的商业站点，后者交付的是一个面向内部的采集流程。
2. **Atoms 的产物是「一个网站」，Atomlet 的产物是「一套持续被填写的数据流」** —— 有显式 schema、有版本、有读写分离的分享权限，数据会持续回流并积累。
3. **Atoms 的迭代是「再对话一次」，Atomlet 的迭代是「打一个补丁」** —— 只改目标页面、版本 +1、可回滚、历史数据不丢，因为业务表格的特性是「稳定演化」，不是「推倒重来」。

## 4 为什么不做通用生成器

这是最容易被追问的一个问题，回答必须承认「通用更大」，然后说明「通用在这个约束下做不出可用」。

| 理由 | 展开 | 若不遵守的后果 |
|---|---|---|
| R1 时间盒约束 | 6.5 小时净工时。通用生成器的最小可用集是「任意页面 + 任意交互 + 任意数据模型」，仅布局系统与组件库就要占满预算 | 做出来是「能生成五花八门但都不能用」的样机，主流程断在填报或分享 |
| R2 验收标准不可定义 | 「生成任意应用」的正确性无法在 48 小时内被验证，只能演示个案；而「表格 → 表单+列表+统计 → 外部填报」的正确性可以逐条打勾 | 面试官无法判断做得好不好，交付物失去说服力 |
| R3 与 Atoms 正面撞车 | Atoms 用多智能体 + Race Mode + Cloud 做通用生成，资源与积累远超单人 | 在对手最强的地方比弱项，且叙事上变成「Atoms 的低配版」 |
| R4 窄场景才有真深度 | 只有锁定场景，「表头→schema 推断」「脏数据报告」「schema 演进不丢数据」这些真正难的问题才会被解决 | 通用路线下这些都只能做表面，反而没有任何一处比对手强 |

**如果时间从 6.5 小时变成 3 个月，我会怎么走**（说明当前边界是时间选择而非能力上限）：第 1-2 周把 AppSpec 从「6 组件」扩到 12 组件并支持页面内组合；第 3-4 周做物理表演进（按 spec 生成表 + 迁移脚本）；第 5-6 周做权限与协作；通用生成放在最后，且仍以「表格驱动」为入口——入口不变，只是出口变宽。

### 4.1 三条技术路线的对比（说明「窄」是路线选择的结果）

| 对比项 | 代码生成（Atoms / Lovable / v0） | 拖拽配置（Retool / 低代码） | 声明式 spec + Runtime（Atomlet） |
|---|---|---|---|
| 产物 | 源码或可部署包 | 平台内的应用配置 | 一个 JSON（AppSpec）+ 固定运行时 |
| 修改一次的代价 | 重新生成或读 diff 改代码 | 手工拖拽 + 改查询 | 生成 JSON Patch，通常 2-8 条 op |
| 修改的可验证性 | 低（要会读代码） | 中（要理解配置） | 高（字段级/页面级 diff 可读） |
| 用户门槛 | 中高 | 高 | 低 |
| 表达力上限 | 最高 | 中 | 最低（6 组件） |
| 单人 6.5h 能否做到端到端可用 | 否 | 否 | **是** |
| 主要风险 | 生成物不可控、失败点分散 | 用户配置错误、学习成本 | 表达力不足，复杂需求接不住 |

读法：**表达力与「端到端可用」在 6.5 小时里是互斥的**。选第三条路线不是因为它最好，而是因为它是唯一能在时间盒内把「生成→填报→分享→修改」全部打通并逐条验证的路线。表达力不足的风险被明确接受，并写进 02 文档的范围外清单。

## 5 被追问时的应答要点

每个回答都按「承认对手优势 → 指出不同约束 → 给出我们的证据」三段组织，避免变成贬低对手。

**Q1「这不就是 Lovable / v0 做一个内部工具吗？」**
生成物不同：Lovable 生成代码，改一次要读懂一次 diff；Atomlet 生成声明式 spec，改动是一条可读的补丁（「新增 region 字段」「stats 加 groupBy」），用户能判断改对没有。另外 Lovable 需要 GitHub 与 Supabase 授权，Atomlet 的外部提交者连账号都没有。可判断性与零门槛，是这一类用户真正缺的东西。

**Q2「为什么不用 Retool 或多维表格？它们更成熟。」**
多维表格确实够用，但它的上限是「表格 + 视图」，做不出「一套有导航、有详情页、有提交校验的内部系统」；Retool 能做到，但要求使用者会建数据模型、写查询、配权限，一线运营不会学。Atomlet 的差异点是从现有表头反推模型，零配置——把「建模」这一步从用户身上拿走了。

**Q3「三阶段智能体是不是包装？一个模型调三次而已。」**
关键不在「几个模型」，在「谁有权否掉谁」。Critic 的三道校验——结构、引用完整性、空数据渲染冒烟——是真实的质量门，删掉它，模型最常见的「page 引用不存在的 entity」就会直接白屏给用户看。让生成方自评是无效的，必须有独立角色做验证，这就是多智能体在这个任务上的必要性；也因此我们不做 Race Mode，因为收益不在质量门上。

**Q4「为什么不做通用一点？市场大得多。」**
在 6.5 小时内做通用，结果一定是样样稀松：主流程断在填报或分享，反而证明不了任何东西。窄场景的价值是「端到端可用」本身可以被逐条验证，而端到端可用恰恰是最难的那一步。范围小是交付策略，不是产品愿景的终点——第 4 节写了时间变成 3 个月时的扩宽路径。

**Q5「JSONB 单表存所有应用的数据，撑得住吗？为什么不按 spec 建表？」**
5000 行/应用、十几个应用的量级下，单表 + app_id 索引 + payload GIN 完全够，查询是毫秒级。不做运行时 DDL 的原因是它会同时引入迁移、回滚、权限、并发四类故障，任何一类都能吃掉整个时间盒；而本产品最高频的操作恰恰是「加字段」，JSONB 下加字段零成本，物理表下要做迁移。演进路径写得很清楚：等数据量与合规要求上来，再按 spec 生成物理表与迁移脚本。

**Q6「48 小时、一个人，做得这么窄，怎么体现能力？」**
窄不等于简单。真正难的四件事都在窄场景里：从混乱表头反推类型与枚举、schema 演进时历史数据不丢、匿名写入的鉴权与幂等、以及「改动只影响目标页面」的补丁校验。另外，主动用时间盒约束范围、预先写清砍功能的顺序，本身就是工程判断的一部分——能收住范围的人比能铺开功能的人少。

**Q7「数据涨到 100 万行怎么办？」**
这个量级的瓶颈不是表数量，是 payload 扫描，所以第一步是按 app_id 分区加覆盖索引，而不是拆表。等单应用真的超过十万行、或出现字段级合规要求，再按 spec 生成物理表并跑迁移脚本；这条路已经在技术方案里留了位置，只是明确不在本 Demo 的范围里。

## 6 一句话总结（放在口头介绍开头）

> Atoms 证明多智能体能造出一个产品；Atomlet 想证明同一套方法能把一线人员手上的一张表，变成一套真的有人在用的系统。
