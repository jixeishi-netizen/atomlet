# 21. 交互式页面支持（真实交互 + 数据持久化）

> 背景：评审给的验收标准是两条——**具备真实交互（而非纯静态展示）**、**具备数据持久化**。
> 用「做一个 2048 游戏」来验证时，系统生成的是「2048 对局记录本」：有表单、有列表、有数据库，但**没有棋盘、没有移动、没有合并**。交互这条不合格。

---

## 1. 根因

问题不在模型，在**能力模型的表达力**：AppSpec 只有五类页面（form / table / detail / stats / board / chart），全部是「数据的容器」，没有「可操作的东西」。模型再聪明，也只能把「游戏」塞进最接近的形态——一张记录表。

结论：要支持交互，必须给 AppSpec 增加一类**交互页**，并在渲染层提供两种实现。

---

## 2. 两类页面，各管一件事

| 类型 | 页面 kinds | 数据来源 | 适合 |
|---|---|---|---|
| 数据页 | form / table / detail / stats | PostgreSQL（`app_records`） | 登记、查询、统计、审批台账 |
| 交互页 | game | 内置引擎状态 / 沙箱内 JS | 游戏、计算器、计时器、抽奖等 |

交互页再分两条实现路径：

| 路径 | `game` 取值 | 谁产出 | 质量 | 覆盖范围 |
|---|---|---|---|---|
| 内置引擎 | `"2048"` | 我们自己写的确定性实现（`src/lib/games/2048.ts`） | 稳定，逻辑有单测 | 只有 2048 |
| 生成实现 | `"custom"` | 模型输出单文件 HTML（内联 CSS/JS） | 取决于模型，但不影响宿主 | 任意交互需求（贪吃蛇、扫雷、计算器…） |

**为什么不全用生成**：2048 是高频试探点，内置引擎保证「问到就一定对」，且逻辑可单测（`npm run check:2048`）。
**为什么不能只做内置**：换一个游戏就废。长尾交给生成实现，这才叫能力，不叫演示脚本。

---

## 3. 安全边界（生成代码不能乱来）

生成的自定义页面跑在 `<iframe sandbox="allow-scripts allow-pointer-lock" srcdoc={html}>` 里：

- **不给 `allow-same-origin`**：脚本处于不透明源，拿不到父页面 DOM、Cookie、`localStorage`，也读不到站点数据
- **不给 `allow-top-navigation` / `allow-popups`**：无法劫持页面跳转
- **无网络**：沙箱内 `fetch` 受 CSP 与源限制，无法外传数据
- 生成结果落库前还要过三道校验（`src/lib/spec/validate.ts`）：
  - `html` 长度 ≥ 200 字符（空白 iframe 判失败）
  - 不得包含 `src="http(s)://"` / `href="http(s)://"` 外部资源（必须自包含）
  - 必须含 `<script>` 或 `<canvas>`（否则不可交互）
- 体积上限 120KB（schema 层），防止异常输出撑爆数据库

---

## 4. 交互页也要能持久化

验收第二条是「数据持久化」。沙箱里没有网络、没有 localStorage，所以做了**受控消息通道**：

```
iframe 内：window.parent.postMessage({ type: 'atomlet:save', data: { game:'贪吃蛇', score: 42 } }, '*')
      ↓
父页面：校验 event.source 必须是本 iframe → POST /api/apps/:id/interactions
      ↓
服务端：写 app_records（entity='_interaction'），限制 8KB，返回 201
      ↓
父页面：显示「成绩已存入数据库（时间）」
```

设计取舍：

- `entity` 用 `_interaction` 而不是套用业务实体——这类数据没有字段约束，硬套 `validateRecordPayload` 只会写不进去
- 只允许父页面代写，不让 iframe 直接调 API（没有同源权限，也避免把 token 暴露给生成代码）
- 失败时页面显式提示，不静默丢弃

---

## 5. 提示词策略（决定生成对不对）

`SCHEMA_BRIEF` 里加了一条最高优先级规则：

1. 只要需求核心是「能操作 / 能玩 / 能用」而不是「记录数据」，**禁止**产出台账类应用
2. 2048 → 内置引擎（给完整示例）
3. 其它 → `game:"custom"` + 完整单文件 HTML（要求内联、可键盘/触摸操作、有重新开始、体积 3–10KB）
4. 需要保存成绩时调用 `postMessage` 通道

用真实模型（deepseek-flash）实测：贪吃蛇 1 次通过，产出 3487 字符的自包含 HTML，含 canvas 与 keydown 监听。

---

## 6. 已知限制

| 限制 | 影响 | 后续 |
|---|---|---|
| 生成质量依赖模型 | 复杂游戏（俄罗斯方块）可能一次写不完整 | 加「渲染后自检」：父页面用 `postMessage` 探活，超时则提示重新生成 |
| iframe 高度固定 560px | 超高内容会滚动 | 由子页面 `postMessage` 上报高度后自适应 |
| 无前端自动化测试 | 交互只能人工验 | 引入 Playwright 后补 E2E |
| `_interaction` 数据不进统计页 | 成绩只在库里，不在 dashboard | 统计页支持 `entity='_interaction'` 的自由字段聚合 |

---

## 7. 复跑方式

```bash
# 引擎单测（纯逻辑）
npm run check:2048

# 真实模型：换一个游戏也能出交互页
curl -sN -X POST localhost:3000/api/apps/generate \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"做一个贪吃蛇游戏，方向键控制，吃到食物变长"}' | tail -1

# 落库通道
curl -s -X POST localhost:3000/api/apps/<appId>/interactions \
  -H 'Content-Type: application/json' -d '{"data":{"game":"snake","score":12}}'
```
