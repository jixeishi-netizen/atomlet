## 1 项目背景与目标

### 1.1 背景

一线业务人员每天都在用 Excel 承接本该由系统承接的工作：门店巡检、报损登记、客户回访、活动报名、设备点检。这些工作的共同特征是表格结构简单（5-15 列）、填写者固定（十几到几十人）、汇总口径固定（按门店/按区域/按周）。

用 Excel 承接只有三个真实浪费，且都不是「表格不好用」：

1. **结构靠默契**：表头就是 schema，没人强制；第 8 行有人把日期写成「10月8日」，第 20 行有人写「10/8」，统计就废了。
2. **校验为零**：必填、枚举、数值范围全靠填的人自觉，回收后要人工洗一遍。
3. **汇总靠人肉**：每周把 8 个门店发来的表粘在一起，用数据透视表算一遍，30-60 分钟，且每次重做。

现有三条解法都不合身：找 IT 排期要 2 周起；买垂直 SaaS 要为 5% 的需求付 100% 的钱，且流程必须迁就产品；低代码平台要求使用者自己会建表、建流程、配权限，一线学不会。

### 1.2 目标

把「一张表格 → 一套能用的内部系统」压缩到 60 秒内，且生成物**当场可填、可分享、可改**。

不追求生成任意 Web 应用（那是 Atoms / Lovable 的战场）。只在一个窄场景做到端到端闭环：**表格驱动的小型录入—汇总系统**。

### 1.3 成功判定（Demo 层面）

四条，不再拆细：

1. 主流程 5 步（导入 → 生成 → 填报 → 分享 → 迭代）在干净浏览器会话下连续跑通 3 次，不依赖手工修数据。
2. 外部设备无账号打开分享链接能提交，回到主应用数据可见。
3. 对话修改只改目标页面、其他页面 diff 为空，且能回滚；每条 P0 验收项都有真机证据（截图/录屏），不靠口头声称。

## 2 目标用户与痛点

### 2.1 三类画像

| 画像 | 典型身份 | 典型场景 | 核心痛点 | 现有替代 | 触发点 |
|---|---|---|---|---|---|
| U1 门店/区域管理者 | 区域督导、连锁店长 | 8-30 家门店每周上报营业额、客流、异常事项；要看区域汇总排名 | 收表耗时、口径不一、看不到趋势；想要「能按区域分组看」但不会提需求 | 微信群 + Excel + 手工透视表 | 周报前夜，或上级要看排名 |
| U2 行政/运营专员 | 行政、活动运营、HR | 办公用品申领、活动报名、资产盘点、培训签到 | 表单分散在问卷工具里，回收后要导出再整理；想加一个字段要求助 IT | 问卷星/腾讯文档 + Excel 二次加工 | 新活动立项，或盘点季 |
| U3 临时收集者 | 项目经理、临时负责人、外部合作方对接人 | 一次性收集 20-200 条信息（供应商资料、候选人登记、售后工单） | 不想注册任何账号、不想搭后端；收集完就要能查能导出 | 共享表格 + 电话催填 | 需要 3 天内收齐一批数据 |

### 2.2 痛点归纳（只保留驱动设计的）

| 编号 | 共性痛点 | 对应设计决策 |
|---|---|---|
| P-1 | 表头即 schema，但没人负责结构 | 由工具型智能体把表头转成显式 AppSpec 字段定义，让结构变成可审阅物 |
| P-2 | 一线填不对，回收后洗数据 | 生成物自带字段级校验（必填/枚举/数值范围），在提交时拦住 |
| P-3 | 汇总每次重算 | 统计卡与分组看板作为一等组件由 spec 声明，不靠用户配 |
| P-4 | 收集要账号、要发链接给外人 | 分享 token 匿名填报，无注册流程 |
| P-5 | 需求变更要等排期 | 对话式增量修改，生成 JSON Patch 而非重新生成整个应用 |

**取舍**：P-1 到 P-5 都能被一个「声明式 AppSpec + 运行时渲染」架构覆盖，这是选它的唯一理由。若做自由布局拖拽编辑器，能覆盖 P-1 但会吃掉全部时间盒，且对 U1/U3 无价值 —— 因此不做编辑器，只做对话修改。

## 3 产品定位与价值主张

**一句话定位**：把一张表格或一句业务痛点，变成一套能用的内部系统。

三层价值，按用户感知顺序：

1. **60 秒成系统**：上传表格后不需建表、不需配权限、不需选模板样式，直接得到表单 + 列表 + 详情 + 统计。
2. **免账号收集**：一条链接发出去，外部用户打开就能填，填完即入库，提交者不注册。
3. **对话即迭代**：说「再加一个区域字段，按区域分组看」，系统生成补丁只改相关页面，版本 +1，可回滚，数据不丢。

**与 Atoms 的边界**：Atoms 面向创业者做「能赚钱的产品」（Landing Page、SaaS、带支付的商业应用）；Atomlet 面向一线业务人员做「把 Excel 变系统」。支付、SEO、自定义域名、代码导出一律不做 —— 不是能力不足，而是这些能力会把目标用户从 U1/U2/U3 换成创业者，产品叙事立刻和 Atoms 撞车。

## 4 术语表

| 术语 | 定义 | 备注 |
|---|---|---|
| AppSpec | 描述一个应用的完整声明式 JSON：`{appId, name, version, theme, entities[], pages[], nav[]}` | 系统的唯一真相源，不是代码片段 |
| Entity | AppSpec 中的数据实体（如「门店日报」），含 `key/label/fields[]` | 一个应用 1-3 个实体 |
| Field | 字段定义：`{key, label, type, required, enum[], ref}`，type 取 text/longtext/number/date/enum/bool/url/ref/user | 9 种类型，与 07/14 的渲染器一一对应；金额、百分比是 number 的展示格式，不是独立类型；文件上传属 P2 |
| Page | 页面声明：`{id, type, title, entity, config}`，type 取 6 类组件之一 | 无自由布局，页面按类型渲染 |
| Component | 固定 6 类渲染单元：form / table / detail / stats / board / chart | 不做拖拽、不做自定义 CSS |
| Runtime | 读取 AppSpec 并渲染页面 + 处理写入的运行时，与生成侧解耦 | 换主题不改 Runtime |
| Planner | 生成侧第一智能体：理解需求，输出实体清单与页面规划 | 只输出规划，不写 spec |
| Builder | 生成侧第二智能体：依据规划输出完整 AppSpec JSON | 受 JSON Schema 约束 |
| Critic | 生成侧第三智能体：三道校验（结构、引用完整性、渲染冒烟），失败带错误回灌 | 最多重试 3 次 |
| Patch | 增量修改产物，JSON Patch（RFC 6902）子集，仅允许在 `/pages[i]`、`/entities[i]` 等白名单路径上操作 | 不重生成整个 spec |
| Version | 应用版本号，单调递增整数；回滚=以旧 spec 生成新版本，不覆盖历史 | v1 → v2 → 回滚生成 v3 |
| ShareToken | 分享链接凭证，12 位 base62 随机串，`/s/{token}`，分 read / write 两种模式 | 不可枚举、不需登录 |
| AppRecord | 一条业务数据，物理存于统一表 `app_records(id, app_id, payload jsonb, ...)` | 按 app_id 隔离 |
| Smoke Render | Critic 的第三道校验：用空数据把 spec 渲染成 DOM，检查 6 类组件不抛错 | 拦住「能存不能渲染」的 spec |
| Seed | 演示用预置数据，应用创建时可选注入 10-20 条 | 仅用于演示与空态兜底 |

### 5.2 M1 需求入口与解析

| 编号 | 需求描述 | 输入 → 输出 | 优先级 | 工时 |
|---|---|---|---|---|
| FR-01 | 支持上传 xlsx/csv（≤5MB，≤5000 行，≤50 列），自动推断每列类型、识别低基数列为枚举、产出脏数据报告（空列名、混合类型、枚举候选超阈值） | 文件 → 字段清单 `[{name, guessedType, sampleValues, enumCandidates, issues}]` | P0 | 0.30 |
| FR-02 | 支持一句话需求输入，抽取实体、字段意图、汇总口径（如「按区域分组看客流」） | 自然语言 → 意图摘要（实体名、字段列表、2-4 个页面类型、分组维度） | P0 | 0.10 |

**设计取舍**：解析器只做「建议 + 可修改」，不做全自动。用户可在生成前改字段名、改类型、把某列标为枚举。理由是推断必然出错，把错误暴露在生成前（成本=点一下）远好于暴露在生成后（成本=重新生成 60 秒）。脏数据报告只报告不阻断，因为脏数据本来就要人判断。

### 5.3 M2 生成链路

| 编号 | 需求描述 | 输入 → 输出 | 优先级 | 工时 |
|---|---|---|---|---|
| FR-03 | 三阶段串行编排，每阶段结果流式推送到前端进度区（阶段名 + 摘要，非原始 token 倾倒） | 意图摘要 → 进度事件流 → 终态 AppSpec | P0 | 0.20 |
| FR-04 | Planner 输出实体清单、字段、页面规划（页面类型 + 绑定实体 + 关键 config） | 意图摘要 → 规划 JSON | P0 | 0.10 |
| FR-05 | Builder 依据规划输出完整 AppSpec，必须通过 JSON Schema 结构约束 | 规划 JSON → AppSpec | P0 | 0.35 |
| FR-06 | Critic 执行三道校验：①结构校验（必填字段、组件名在 6 类白名单内）②引用完整性（page.entity 存在、field.ref 指向存在的 entity、enum 值非空）③渲染冒烟（空数据 SSR 不抛错） | AppSpec → 通过 / 错误清单 | P0 | 0.30 |
| FR-07 | 校验失败把错误清单回灌给 Builder 重试，最多 3 次；第 3 次仍失败则降级输出「最小可用 spec」（1 实体 + form + table）并显式告知用户 | 错误清单 → 新 AppSpec | P0 | 0.10 |
| FR-08 | 生成结果先进入「审阅态」：展示实体与页面列表，用户确认后才落库为 v1 并渲染 | AppSpec → 审阅页 → v1 | P0 | 0.05 |

**设计取舍**：为什么必须 Critic 而不是只靠结构化输出。实测中模型最容易犯的错是「page 引用了不存在的 entity」和「chart 绑了一个 text 字段」——这两类错 JSON Schema 查不出来，但会让渲染直接白屏。用 Critic 在落库前拦掉，比在用户面前白屏后再修便宜。降级到最小 spec 而非直接报错，是因为 Demo 场景下「有一个能填表单的应用」远好于「一个红字报错页」。

### 5.4 M3 运行时渲染

| 编号 | 需求描述 | 输入 → 输出 | 优先级 | 工时 |
|---|---|---|---|---|
| FR-09 | 组件注册表 + 主题令牌（颜色/间距/圆角/字号 4 组变量），按 `page.type` 分发到组件 | AppSpec.page → React 节点 | P0 | 0.20 |
| FR-10 | form 组件：按 field.type 渲染控件，必填标记、提交前校验、行内错误提示、成功反馈 | AppSpec.entity + 提交 → 校验结果 | P0 | 0.35 |
| FR-11 | table 组件：列由 entity 生成、分页、按列排序、关键字搜索、行点击进 detail | 记录集 → 表格 | P0 | 0.30 |
| FR-12 | detail 组件：以只读字段列表展示单条记录，含创建时间 | record → 详情视图 | P0 | 0.15 |
| FR-13 | stats 组件：按 config 声明的聚合（count / sum / avg + 分组维度）渲染统计卡，默认 4 张 | 记录集 + 聚合声明 → 数值卡 | P0 | 0.15 |
| FR-14 | chart 组件：按分组维度画柱状/折线图，无数据时显示空态 | 记录集 + 分组声明 → 图 | P1 | 0.20 |
| FR-15 | 应用外壳：侧边导航由 page 列表生成、页面切换不刷新、空态与加载骨架 | AppSpec → 布局 | P0 | 0.15 |

**设计取舍**：固定 6 组件、不做自由布局拖拽。拖拽编辑器的实现成本约 3-4 小时（含撤销、吸附、响应式、序列化），吃掉一半预算却只换来「看起来更自由」。而 U1/U2/U3 的真实需求是「表单能填、列表能查、数字能汇总」，6 个组件已覆盖 95%。图表被定为 P1，是唯一一个「删掉不影响主流程成立」的组件，因此它排在变更控制的第一顺位（见 10 文档）。

### 5.5 M4 数据与分享

| 编号 | 需求描述 | 输入 → 输出 | 优先级 | 工时 |
|---|---|---|---|---|
| FR-16 | 记录写入：统一表 `app_records(id, app_id, payload jsonb, source, created_at)`，写入前按 AppSpec 做字段级校验（必填、类型、枚举、数值范围、字符串长度 ≤2000），不合法拒绝并返回字段级错误 | payload → record | P0 | 0.30 |
| FR-17 | 记录读取：按 app_id 隔离查询，支持分页（每页 20）、按列排序、关键字模糊匹配 payload 字段 | 查询参数 → 记录集 + 总数 | P0 | 0.15 |
| FR-18 | 分享链接：为应用生成 write / read 两种 token，存 `shares(token, app_id, mode, created_at)`，可复制、可重新生成（旧 token 立即失效） | 应用 → URL `/s/{token}` | P0 | 0.20 |
| FR-19 | 匿名填报页：按 token 取当前版本 spec 渲染 form，无需登录；提交成功显示回执；同一浏览器 60 秒内重复提交同一内容按幂等去重 | token + payload → 入库 | P0 | 0.20 |
| FR-20 | 只读分享视图：read token 渲染 table + stats，无提交入口，服务端拒绝该 token 的写请求 | token → 只读视图 | P1 | 0.15 |

**持久化口径（必须准确表述）**：逻辑上「一个应用一套数据模型」，物理上 MVP 阶段**所有应用共用 `app_records` 一张表 + JSONB payload + app_id 隔离 + 字段级 schema 校验在应用层执行**，**不做运行时 DDL，不自动建物理表**。演进路径才是「按 spec 生成物理表 + 迁移脚本」，属于范围外。理由：运行时 DDL 会引入迁移、回滚、权限、并发四类故障，任何一类都能吃掉整个时间盒；而 JSONB 单表在 5000 行量级下查询性能足够，且 schema 演进（加字段）零成本 —— 这恰好是本产品最高频的操作。

**安全取舍**：token 12 位 base62（约 71 bit 熵），不可枚举；read token 的写请求在服务端拒绝，不只靠前端隐藏按钮；限流 10 次/分钟/IP；payload ≤64KB；关键字搜索参数化查询，不拼 SQL。

### 5.6 M5 增量修改与版本

| 编号 | 需求描述 | 输入 → 输出 | 优先级 | 工时 |
|---|---|---|---|---|
| FR-21 | 对话面板：在应用内输入修改诉求，上下文 = 当前 spec + 最近 6 轮对话 + 字段/页面清单摘要 | 用户原话 → 修改请求 | P0 | 0.20 |
| FR-22 | Patch 生成与三段校验：①必须是合法 JSON Patch 且路径命中白名单（`/name`、`/theme/*`、`/entities/{i}/*`、`/pages/{i}/*`、增删页面）②应用后 spec 仍通过 Critic 三道校验 ③破坏性变更（删除被引用字段、改字段类型）需在 diff 中高亮并二次确认 | 修改请求 → Patch → 新 spec 草稿 | P0 | 0.35 |
| FR-23 | 版本管理：每次接受修改即 version+1，写 `app_versions(app_id, version, spec, patch, message, created_at)`；回滚 = 以目标版本 spec 生成**新**版本（不删历史、不覆盖）；数据不迁移不删除，旧字段数据保留在 payload 中 | 版本选择 → 新版本 | P0 | 0.30 |
| FR-24 | 变更 diff 预览：以「页面级 + 字段级」摘要展示改了什么（新增/修改/删除），用户确认后才生效 | 新旧 spec → diff 摘要 | P1 | 0.15 |

**设计取舍**：为什么用 Patch 而不是重新生成。重生成 60 秒、不确定、且用户此前的微调会丢；Patch 只需一次小模型调用、结果可 diff、可拒绝。代价是 Patch 表达力有限（做不了「整体重设计」），这个限制被接受 —— 主流程里用户要的是加字段、改枚举、加分组，都在 Patch 射程内。

**回滚为什么不覆盖**：如果 v2 回滚到 v1 时直接覆盖为 v1，用户会失去 v2 的痕迹，也无法「再回到 v2 看看」。生成 v3（内容等于 v1）保留完整时间线，实现上只是多插一行，成本几乎为零。

### 5.7 M6 体验与演示

| 编号 | 需求描述 | 输入 → 输出 | 优先级 | 工时 |
|---|---|---|---|---|
| FR-25 | 场景模板库：4 个内置模板（门店日报、办公用品申领、活动报名、设备点检），点击即用，模板 = 预置 AppSpec | 模板选择 → 应用 | P0 | 0.25 |
| FR-26 | 演示种子数据：应用创建时可选注入 12 条示例记录，覆盖多枚举值以便看板/图表有内容 | 应用 → 12 条记录 | P0 | 0.10 |
| FR-27 | 失败可恢复：生成超时/校验连败/网络错误均有明确文案 + 「重试/改用最小 spec/返回」三个出口，已上传文件与已填输入不丢失 | 错误 → 可恢复状态 | P0 | 0.20 |
| FR-28 | 演示动线引导：首页三张卡片明确「上传表格 / 描述需求 / 用模板」，生成后出现一次性的「下一步：填一条记录」气泡 | 无 | P1 | 0.20 |
| FR-29 | 响应式与视觉打磨：375px 宽度下可完成填报；统一间距/圆角/字重；空态插画用文字 + 图标，不引外部图片 | 无 | P1 | 0.25 |

**设计取舍**：模板库的目的不是「功能丰富」，而是**保证演示不会因为 LLM 抖动而失败**。模板走的是预置 spec 直出，零模型调用，是整条链路的兜底演示路径。这一个决定让「演示时挂了怎么办」这个问题消失。

## 6 非功能性需求

### 6.1 性能

| 编号 | 指标 | 目标 | 测量方法 | 关联 FR |
|---|---|---|---|---|
| NFR-P1 | 一句话/表格生成端到端耗时 | P90 ≤ 60s，硬超时 90s 中断并提示 | 服务端计时，记录 10 次取 P90 | FR-03 ~ FR-07 |
| NFR-P2 | 首页与应用首屏 | P90 ≤ 2s（本地 dev 与线上同口径，4G 网络模拟） | Lighthouse + 真机秒表 | FR-15 |
| NFR-P3 | 记录提交响应 | P90 ≤ 500ms（单条 insert + 索引命中） | 接口计时 | FR-16 |
| NFR-P4 | 列表首屏查询 | P90 ≤ 800ms（5000 行内，分页 20） | 接口计时 | FR-17 |

**取舍**：60s 的生成预算拆分为 Planner 12s / Builder 35s / Critic 8s，每次重试追加约 40s。这意味着最多只能容纳 1 次重试落在预算内，第 2、3 次重试会突破 60s。因此把 P90 定在 60s、把上限定在 90s，并在 UI 上把重试状态显式告知（「校验未通过，正在修正第 2 次」），让等待可解释。不追求更快的唯一原因是：三阶段串行是保证 spec 质量的前提，并行化会牺牲 Critic 的拦截率。

### 6.2 可靠性

| 编号 | 要求 | 落地方式 |
|---|---|---|
| NFR-R1 | 生成失败率 < 10%（以 10 次连续真实输入统计） | Critic 三道校验 + ≤3 次回灌 + 最小 spec 降级 |
| NFR-R2 | 任何失败都不产生「半成品应用」 | AppSpec 落库是单个事务，审阅通过才写 v1 |
| NFR-R3 | 失败可恢复，已上传文件与已填输入保留在客户端状态 | 失败不清空表单，重试复用同一输入 |
| NFR-R4 | 数据不因 schema 变更丢失 | 加字段不写历史数据；改类型只影响后续写入与展示格式化，payload 原值保留 |
| NFR-R5 | 并发写入不互相覆盖 | 每条记录独立 insert，无共享行更新 |

### 6.3 可用性

1. 分享侧（外部填报）**零账号**：打开即填，不需要手机号、邮箱、验证码。
2. 主应用侧 Demo 阶段单用户，不做登录墙，但页面明确标注「演示环境」，避免误解为生产可用。
3. 表单错误提示定位到字段，文案说明「怎么改」而不是「错了」；中文优先，不引入 i18n 框架。

### 6.4 安全

| 编号 | 要求 | 落地方式 |
|---|---|---|
| NFR-S1 | 分享链接鉴权 | token 12 位 base62，服务端按 token 反查 app_id 与 mode，不接受客户端传入 app_id |
| NFR-S2 | 读写权限分离 | read token 的 POST 请求由服务端拒绝并返回 403 |
| NFR-S3 | 上传限制 | 仅 xlsx/csv，≤5MB，≤5000 行，≤50 列，超限明确拒绝 |
| NFR-S4 | 输入校验不以客户端为准 | 所有字段校验在写入前于服务端重跑一遍 |
| NFR-S5 | 注入防护 | 查询参数化；payload 中的字符串在渲染时转义，不使用 `dangerouslySetInnerHTML` |
| NFR-S6 | 敏感信息 | 不存用户凭据；LLM API Key 仅在服务端环境变量中，不下发前端 |

## 7 约束与假设

| 类别 | 内容 | 影响 | 应对 |
|---|---|---|---|
| 时间 | 净工时 6.50h，硬上限 7h | 决定范围必须窄，P1 可砍 | 变更控制按 10 文档顺序砍 |
| 人力 | 单人全栈 + AI 辅助 | 上下文切换成本高 | 按 Epic 串行，不并行多模块 |
| 技术 | 单一 LLM Provider + 结构化输出模式；单区域托管 | 无多模型路由、无容灾 | 模板直出作为兜底路径 |
| 数据 | 演示数据量 ≤5000 行/应用 | JSONB 单表可承受 | 不做过早优化 |
| 假设-A1 | 用户上传的表格有明确首行表头 | 解析器按首行取列名 | 首行为空时向下找第一行非空 |
| 假设-A2 | 单应用实体数 ≤3、页面数 ≤8 | 控制 Builder 输出长度与生成延迟 | Planner 最多规划 8 页，超限按优先级截断 |
| 假设-A3 | 用户不感知物理存储形态；演示环境单实例无并发压力 | 可用 JSONB 单表，不做锁与队列 | 逻辑层始终表述为「一个应用一套模型」 |

## 8 范围外清单

| 不做项 | 理由 | 若被追问 |
|---|---|---|
| 多人协作编辑 | 需要 OT/CRDT 与在线状态，成本 ≥2h，与 Demo 主流程无关 | 「协作是规模化之后的问题，MVP 阶段先保证单人能改对」 |
| Stripe 支付 | 服务创业者而非业务人员，做了会改变产品叙事 | 「Atomlet 的交付物是内部数据，不是交易」 |
| SEO / 自定义域名 | 应用是内部工具，不需要被搜索引擎索引 | 「分享链接已满足收集需求，域名是品牌需求」 |
| 代码导出 | 导出即承认「生成物是代码」，与 AppSpec 声明式路线冲突 | 「导出会锁死 spec 演进，用户也需要接管维护」 |
| 通用代码沙箱 | 安全与沙箱成本远超时间盒 | 「只渲染声明式组件，因此不存在任意代码执行」 |
| 移动原生端 | 响应式网页已够，原生是重复建设 | 「375px 可完成填报即为可用」 |
| 运行时建物理表 / 数据迁移 | 迁移、回滚、权限、并发四类故障不可控 | 「演进路径已写清，MVP 用统一表 + JSONB」 |

## 9 验收总则

1. 主流程 5 步（导入 → 生成 → 填报 → 分享 → 迭代）在**全新浏览器会话**下连续 3 次跑通，中途不允许手工改数据库、不允许重启服务。
2. 每条 P0 验收项（见 04 文档）都必须能在真人操作下复现，有截图或录屏，不接受「代码里写了」。
3. 数据持久化以**刷新页面 + 换浏览器 + 外部设备打开分享链接**三重方式验证，三者都能看到同一条数据。
4. 生成失败必须可观察：故意用一张表头混乱的表触发，系统应给出可读原因与重试入口，而不是白屏或无限 loading。
5. 增量修改必须可验证「只改目标」：修改前后导出两份 spec，非目标页面的 diff 为空。
6. 时间盒超支时按 10 文档变更控制顺序砍 P1，砍完后主流程五步仍必须完整可跑。
