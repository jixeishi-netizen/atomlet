## 1. 本轮修复的 4 项与可断言的证据

| # | 缺陷 | 修复落地位置 | 可以直接断言的证据 |

## 2. 环境与判定口径（先读这三条，否则会误判）

**① 项目目录是 `~/atomlet`（= `/root/atomlet`）。** 本文档所有命令都在这里执行。之前的验收文档把目录写成了 `/opt` 下的一个同名目录，那是错的：在 `/opt` 那个路径下没有 `docker-compose.yml`，`docker compose` 会报 `no configuration file provided`。

**② 生产库现在应有 6 张表**：`apps`、`app_versions`、`app_records`、`share_links`、`gen_runs`、`messages`。第 6 张来自 `drizzle/0001_messages.sql`。如果只有 5 张，说明迁移没执行，跑 R-01 第 0 步补上（该 SQL 是幂等的，重复执行不报错）。

**③ 时间是否修好，只看页面渲染出来的时间。** `docker compose exec web date` 显示 UTC 不构成缺陷：

- `node:20-alpine` 默认不带 `tzdata`，`TZ=Asia/Shanghai` 对**系统 time** 是否生效取决于镜像是否用最新 `Dockerfile`（含 `apk add --no-cache tzdata`）重新构建过；
- 页面时间走 `src/lib/format.ts` 的 `Intl.DateTimeFormat('zh-CN', { timeZone: 'Asia/Shanghai' })`，**与容器系统时区无关**，所以即使容器 `date` 是 UTC，页面时间依然正确。

因此 `date` 只能作为附加证据，R-04 的判定只认页面渲染值。

## 3. 公共准备（每开一个新终端跑一次）

```bash
cd ~/atomlet
LOCAL=http://127.0.0.1:3000
EXT=http://118.178.174.105:3000

PSQL() { docker compose exec -T db psql -U atomlet -d atomlet -tAc "$1"; }
```

命令约定：

1. `PSQL "..."` 就是 `docker compose exec -T db psql -U atomlet -d atomlet -tAc "..."`。`-T` 必须带，否则 `exec` 会尝试分配 TTY，在脚本或管道里报 `the input device is not a TTY`。
2. 生成接口返回 `text/event-stream`，每行是 `data: {...}`；业务失败时 **HTTP 仍是 200**，失败信息在流内的 `{"t":"error"}` 事件里。判定看流内事件，不看 HTTP 码。
3. 应用 ID 一律从库里取（`order by created_at desc limit 1`），字段 key 一律从 `spec` 里读。用户的应用由模型生成，字段名不在文档里硬编码。
4. `R-01` / `R-02` / `R-03` 各自会新建一个应用（每次约 4–10 秒），互不复用，避免前一条用例的改动影响后一条。

## 4. 用例

### R-01 对话历史持久化【缺陷 1】

**覆盖维度**：`messages` 表落库、生成/改需求/回滚三条链路的留痕、degraded 分支留痕、刷新后历史仍在、页面文案与库内行数一致。

**前置条件**
- `cd ~/atomlet`，已执行 §3 公共准备。
- `.env` 中 `LLM_PROVIDER=openai` 且 `LLM_API_KEY` 非空（模型通道可用）。

**执行步骤**

第 0 步：确认迁移已执行（输出 `0` 才需要跑第二行，SQL 幂等）

```bash
PSQL "select count(*) from pg_tables where schemaname='public' and tablename='messages'"
docker compose exec -T db psql -U atomlet -d atomlet < drizzle/0001_messages.sql
```

第 1 步：生成一个应用，生成过程应写入 2 条消息

```bash
curl -sN -X POST $LOCAL/api/apps/generate \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"做一个办公用品领用登记：领用人、部门、物品名称、数量、领用日期"}' \
  | tee /tmp/r01_gen.log | tail -2

APP_ID=$(grep -o '"appId":"[^"]*"' /tmp/r01_gen.log | head -1 | cut -d'"' -f4)
echo "APP_ID=$APP_ID"

PSQL "select count(*) from messages where app_id='$APP_ID'"
PSQL "select role, version, left(content, 50) from messages where app_id='$APP_ID' order by created_at"
```

第 2 步：页面应渲染出对话历史（服务端渲染，`curl` 可直接断言）

```bash
curl -s "$LOCAL/apps/$APP_ID" > /tmp/r01_p1.html
grep -c '刷新页面不会丢' /tmp/r01_p1.html
grep -o '共 [0-9]* 条' /tmp/r01_p1.html | head -1
grep -c '已生成「' /tmp/r01_p1.html
```

第 3 步：一次「没听懂」的指令 —— degraded 分支也必须留痕

```bash
curl -sN -X POST $LOCAL/api/apps/$APP_ID/chat \
  -H 'Content-Type: application/json' \
  -d '{"instruction":"今天天气怎么样"}' | tee /tmp/r01_chat_deg.log | tail -2

PSQL "select count(*) from messages where app_id='$APP_ID'"
PSQL "select role, left(content, 60) from messages where app_id='$APP_ID' order by created_at desc limit 2"
```

第 4 步：一次能落地的指令 —— 成功分支留痕且版本前进

```bash
curl -sN -X POST $LOCAL/api/apps/$APP_ID/chat \
  -H 'Content-Type: application/json' \
  -d '{"instruction":"加一个字段：备注说明"}' | tee /tmp/r01_chat_ok.log | tail -2

PSQL "select current_version from apps where id='$APP_ID'"
PSQL "select count(*) from messages where app_id='$APP_ID'"
PSQL "select role, version, left(content, 60) from messages where app_id='$APP_ID' order by created_at desc limit 2"
```

第 5 步：回滚也要留痕（只写一条 assistant，没有用户指令）

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST $LOCAL/api/apps/$APP_ID/versions/1/rollback

PSQL "select count(*) from messages where app_id='$APP_ID'"
PSQL "select role, version, left(content, 60) from messages where app_id='$APP_ID' order by created_at desc limit 1"
```

第 6 步：刷新两次，历史完全一致

```bash
curl -s "$LOCAL/apps/$APP_ID" > /tmp/r01_p2.html
curl -s "$LOCAL/apps/$APP_ID" > /tmp/r01_p3.html
grep -o '共 [0-9]* 条' /tmp/r01_p2.html | head -1
grep -o '共 [0-9]* 条' /tmp/r01_p3.html | head -1
diff <(grep -o '共 [0-9]* 条' /tmp/r01_p2.html) <(grep -o '共 [0-9]* 条' /tmp/r01_p3.html) && echo "两次刷新一致"
grep -c '已生成「' /tmp/r01_p3.html
grep -c '未产生新版本' /tmp/r01_p3.html
grep -c '已回滚到 v1' /tmp/r01_p3.html
```

**期望结果**

| 步骤 | 期望输出 |
|---|---|
| 0 | 第一行输出 `1`（表已存在）；若为 `0`，第二行执行完再查一次得 `1` |
| 1 | 流内最后一条为 `{"t":"saved",...}`；`count(*)` 输出 `2`；两行依次为 `user|1|<原始需求文本>`、`assistant|1|已生成「<应用名>」：…` |
| 2 | `刷新页面不会丢` 命中 `1`；`共 2 条`；`已生成「` 命中 `1` |
| 3 | 流内 `{"t":"done",...,"degraded":true}`；`count(*)` 输出 `4`；最新两行为 `user|<指令原文>` 与 `assistant|1|未产生新版本（仍为 v1）：…` |
| 4 | 流内 `{"t":"done","versionNo":2,...}`；`current_version` 输出 `2`；`count(*)` 输出 `6`；最新一条 assistant 内容以 `已生成 v2：应用` 开头 |
| 5 | `HTTP 200`，响应 `{"versionNo":3,"rolledBackFrom":2,"rolledBackTo":1}`；`count(*)` 输出 `7`；最新一条内容为 `已回滚到 v1，当前版本 v3（旧版本仍保留）。` |
| 6 | 两次都输出 `共 7 条` 且 `diff` 无输出；`已生成「`、`未产生新版本`、`已回滚到 v1` 三个计数都 ≥ `1` |

**判定标准**

`messages` 表里该应用的 7 条记录存在（2 生成 + 2 降级 + 2 成功 + 1 回滚），页面显示 `共 7 条`，且刷新两次后三类文案仍能在 HTML 里找到，即为通过。只看「页面上有字」不算通过——行数与 `共 N 条` 必须对齐。

**失败排查**

| 现象 | 原因 | 修复命令 |
|---|---|---|
| 第 1 步 `count(*)` 输出 `0`，页面无对话区 | `drizzle/0001_messages.sql` 未执行；或 `appendMessage` 写库抛错被吞（它设计上不阻断主流程） | `docker compose logs --tail=100 web \| grep '\[messages\]'`；有 `写入失败` 就先建表：`docker compose exec -T db psql -U atomlet -d atomlet < drizzle/0001_messages.sql` |
| 第 3 步 `count(*)` 只加了 1 条 | 指令被模型正常处理成了一次修改（不是 degraded），走了成功分支 | 换一句与业务完全无关的指令重试（如 `今天星期几`）；已有记录不删，按实际分支核对文案即可 |
| 第 6 步 `共 N 条` 与库内 `count(*)` 不一致 | 页面只渲染最近 60 条（`listMessages(appId, 60)`），历史超过 60 条时页面数字会封顶在 60 | `PSQL "select count(*) from messages where app_id='$APP_ID'"` 与页面数字一起看；超过 60 属设计行为，不算缺陷 |

### R-03 金额下限（浏览器路径 + 接口路径）【缺陷 3】

**覆盖维度**：自然语言约束落成 `min`、生成流里的补全提示、服务端 422 兜底文案带下限值、边界值 `0.01` 可通过、表单端提交前自拦截且不发请求。

**前置条件**
- `cd ~/atomlet`，已执行 §3 公共准备；模型通道可用。
- 需求里必须同时出现「约束词」和「金额类字段名」：约束词命中 `大于 0`、`不能为 0`、`必须为正`、`至少 1`、`不为 0`；字段标签命中 `金额`、`费用`、`价格`、`成本`、`工资`。本文档给的需求把两者都写进去了。

**执行步骤**

第 1 步：生成一个带「金额大于 0」需求的应用

```bash
curl -sN -X POST $LOCAL/api/apps/generate \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"做一个费用报销登记：报销人、部门、费用金额、报销日期、费用说明，金额大于 0"}' \
  | tee /tmp/r03_gen.log | tail -3

APP2=$(grep -o '"appId":"[^"]*"' /tmp/r03_gen.log | head -1 | cut -d'"' -f4)
TOKEN2=$(grep -o '"shareToken":"[^"]*"' /tmp/r03_gen.log | head -1 | cut -d'"' -f4)
echo "APP2=$APP2 TOKEN2=$TOKEN2"
```

第 2 步：生成流里应出现下限补全提示，spec 里该字段应带 `min`

```bash
grep -o '按需求补充了字段下限约束：[^"]*' /tmp/r03_gen.log | head -1

PSQL "select f->>'key', f->>'label', f->>'min' from app_versions v, jsonb_array_elements(v.spec->'entities'->0->'fields') f where v.app_id='$APP2' and v.version=1 and f->>'type'='number'"

MKEY=$(PSQL "select f->>'key' from app_versions v, jsonb_array_elements(v.spec->'entities'->0->'fields') f where v.app_id='$APP2' and v.version=1 and f->>'type'='number' and (f->>'min')::numeric > 0 limit 1")
echo "MKEY=$MKEY"
```

第 3 步：准备好合法 payload 并注入金额值

```bash
mkp() {  # $1=要覆盖的字段 key，$2=覆盖值；不带参数则全部取合法值
  PSQL "select jsonb_object_agg(f->>'key', case
      when '$1' <> '' and f->>'key' = '$1' then to_jsonb('$2'::text)
      when f->>'type'='number' then to_jsonb(1)
      when f->>'type'='date' then to_jsonb(to_char(current_date,'YYYY-MM-DD')::text)
      when f->>'type'='bool' then 'true'::jsonb
      when f->>'type'='enum' then to_jsonb(coalesce(f->'enum'->>0,'A')::text)
      when f->>'type'='url' then to_jsonb('https://example.com'::text)
      else to_jsonb('回归样本'::text) end)::text
    from app_versions v, jsonb_array_elements(v.spec->'entities'->0->'fields') f
    where v.app_id='$APP2' and v.version=(select current_version from apps where id='$APP2')
      and f->>'type' not in ('ref','user')"
}

echo "合法 payload: $(mkp)"
```

第 4 步：接口路径 —— 写 0 必须被 422 拦下，写 0.01 必须通过

```bash
# 4a 金额 0 → 422
curl -s -w "\nHTTP %{http_code}\n" -X POST "$LOCAL/api/public/$TOKEN2/records" \
  -H 'Content-Type: application/json' -d "{\"payload\":$(mkp "$MKEY" 0)}"

# 4b 金额 0.01（边界值）→ 201
curl -s -w "\nHTTP %{http_code}\n" -X POST "$LOCAL/api/public/$TOKEN2/records" \
  -H 'Content-Type: application/json' -d "{\"payload\":$(mkp "$MKEY" 0.01)}"

# 4c 库内核对：只应有 0.01 那条，没有 0 元记录
PSQL "select count(*) as total, count(*) filter (where (payload->>'$MKEY')::numeric > 0) as gt0, count(*) filter (where (payload->>'$MKEY')::numeric = 0) as zero_rows from app_records where app_id='$APP2'"

# 4d 应用内接口同样拦截（同一个校验实现）
curl -s -w "\nHTTP %{http_code}\n" -X POST "$LOCAL/api/apps/$APP2/records" \
  -H 'Content-Type: application/json' -d "{\"payload\":$(mkp "$MKEY" -1)}"
```

第 5 步：浏览器路径 —— 表单端在提交前就拦住，不发请求

```bash
echo "填报地址：$EXT/p/$TOKEN2"
```

在浏览器打开上一步打印的地址，按顺序做：

1. `F12` 打开 DevTools → `Network` 面板，勾选 `Fetch/XHR`；
2. 金额输入框填 `0`，其余必填项照填；
3. 点提交按钮；
4. 观察：输入框下方出现红色文案，`Network` 面板**不新增请求**；
5. 金额改成 `0.01`，再点提交；
6. 观察：出现成功提示，`Network` 面板出现 1 条 `records` 请求且状态 `201`。

**期望结果**

| 步骤 | 期望输出 |
|---|---|
| 1 | 流内最后一条为 `{"t":"saved",...}`；`APP2` 为 36 位 UUID |
| 2 | 提示行形如 `按需求补充了字段下限约束：费用金额 ≥ 0.01`；字段表里该数字字段 `min=0.01`；`MKEY` 为该字段的 key（如 `expense_amount`） |
| 3 | 打印出的 payload 是合法 JSON 对象，金额字段值为 `1` |
| 4a | `{"error":"校验未通过","fieldErrors":{"<MKEY>":"<label>必须大于 0（最小 0.01）"}}`，`HTTP 422` |
| 4b | `{"ok":true,"record":{...}}`，`HTTP 201` |
| 4c | `total=1`、`gt0=1`、`zero_rows=0` |
| 4d | `HTTP 422`，`fieldErrors` 文案为 `<label>必须大于 0（最小 0.01）`（`-1` 与 `0` 命中同一条 `min` 分支，文案只取决于字段的 `min` 值，与传入值无关） |
| 5 | 浏览器：填 0 时出现 `必须大于 0（最小 0.01）` 且 `Network` 无新请求；填 0.01 时请求返回 201 并提示成功 |

**判定标准**

服务端（4a）对 0 返回 422 且文案带出下限值 `0.01`，边界值 `0.01` 能写入（4b / 4c 无 0 元记录），且浏览器（5）填 0 时被表单拦下、`Network` 面板没有发出请求、改成 0.01 后能提交成功，即为通过。只验接口 = 只证明兜底；只验浏览器 = 没证明服务端。两条都要。

**失败排查**

| 现象 | 原因 | 修复命令 |
|---|---|---|
| 第 2 步 `MKEY` 为空，生成流里没有补全提示 | 模型把金额字段命名成不含关键词的标签（如「报销额度」），`applyConstraintHints` 的 `MONEY_LABEL_RE` 只认 `金额/费用/价格/成本/工资` | `PSQL "select f->>'label' from app_versions v, jsonb_array_elements(v.spec->'entities'->0->'fields') f where v.app_id='$APP2' and v.version=1 and f->>'type'='number'"`；把需求改成含「费用金额」的措辞重新生成第 1 步 |
| 4a 返回 201（0 元被接受） | 服务端没走 `validateRecord.ts`，或 `min` 没落进 spec | `grep -n 'validateRecord' src/app/api/public/\[token\]/records/route.ts`；`PSQL "select f->>'min' from …"` 确认非空；`docker compose up -d --build web` |
| 5 中填 0 仍发出请求 | `FormPage` 的自校验被跳过（改了提交流程） | `grep -n 'validateRecordPayload' src/runtime/pages/FormPage.tsx`；确认提交前有 `const local = validateRecordPayload(...)` 且 `!local.ok` 时 `return`；重建镜像 |

### R-04 时间显示（北京时间）【缺陷 4】

**覆盖维度**：页面渲染时间与 `Asia/Shanghai` 渲染值一致、不等于 UTC 渲染值、容器系统时间（附加证据）、`tzdata` 依赖说明。

**前置条件**
- `cd ~/atomlet`，已执行 §3 公共准备。
- 库内至少有一个应用（R-01 ~ R-03 已生成过）。

**执行步骤**

第 1 步：算出「正确值」与「错误值」

```bash
APP3=$(PSQL "select id from apps order by created_at desc limit 1")
echo "APP3=$APP3"

EXPECT=$(PSQL "select to_char(created_at AT TIME ZONE 'Asia/Shanghai','YYYY-MM-DD HH24:MI') from apps where id='$APP3'")
UTCS=$(PSQL "select to_char(created_at AT TIME ZONE 'UTC','YYYY-MM-DD HH24:MI') from apps where id='$APP3'")
echo "EXPECT(北京时间)=$EXPECT"
echo "UTCS(UTC)=$UTCS"
```

第 2 步：首页渲染的应用创建时间必须等于 `EXPECT`

```bash
curl -s "$LOCAL/" > /tmp/r04_home.html
grep -c "$EXPECT" /tmp/r04_home.html
grep -c "$UTCS" /tmp/r04_home.html
```

第 3 步：对话消息的时间（同一套格式化函数，`HH:MM`）

```bash
HHMM=$(PSQL "select to_char(created_at AT TIME ZONE 'Asia/Shanghai','HH24:MI') from messages where app_id='$APP3' order by created_at limit 1")
echo "HHMM(北京时间)=$HHMM"
curl -s "$LOCAL/apps/$APP3" | grep -c "$HHMM"
```

第 4 步：容器系统时间（附加证据，不参与判定）

```bash
docker compose exec -T web date
docker compose exec -T web date -u
docker compose exec -T web sh -c 'ls /usr/share/zoneinfo/Asia/Shanghai'
docker compose exec -T db date
```

**期望结果**

| 步骤 | 期望输出 |
|---|---|
| 1 | `EXPECT` 与 `UTCS` 相差 8 小时（`EXPECT` 比 `UTCS` 晚 8 小时） |
| 2 | `grep -c "$EXPECT"` ≥ `1`；`grep -c "$UTCS"` = `0` |
| 3 | `HHMM` 命中 ≥ `1`（消息时间按北京时间渲染） |
| 4 | 最佳：`web date` 显示 `CST` 且与 `EXPECT` 同一小时；`/usr/share/zoneinfo/Asia/Shanghai` 存在。若显示 `UTC` 或该文件不存在，说明镜像没带 `tzdata`——**不影响本用例判定**，处理方式见备注 |

**判定标准**

首页上面板渲染出的应用创建时间字符串等于 `at time zone 'Asia/Shanghai'` 的渲染值，且在同一次响应里**找不到** UTC 渲染值，即为通过。容器 `date` 不是判定项。

> 备注（tzdata 依赖）：`node:20-alpine` 默认不带时区库，`Dockerfile` runner 阶段已加 `apk add --no-cache tzdata`。但只有在**用最新 Dockerfile 重新构建**过的镜像上，`TZ=Asia/Shanghai` 才对系统 time 生效。页面时间来自 `src/lib/format.ts` 的 `Intl.DateTimeFormat(..., { timeZone: 'Asia/Shanghai' })`，与系统 time 无关，所以容器 `date` 是 UTC 时页面仍然正确。要让容器自身也显示 CST：`docker compose up -d --build web`。

**失败排查**

| 现象 | 原因 | 修复命令 |
|---|---|---|
| 第 2 步 `EXPECT` 命中 `0`，`UTCS` 命中 ≥1 | 页面在用进程本地时区格式化（旧实现） | `grep -n 'getHours\|getMinutes\|toLocaleString()' src/lib/format.ts src/runtime/pages/*.tsx`；确认 `formatDateTime` / `formatTime` 走 `Intl` 且带 `timeZone: 'Asia/Shanghai'`；`docker compose up -d --build web` |
| 第 2 步两个都命中 | 库里有另一个应用的创建时间刚好比该应用早/晚 8 小时，`grep` 撞值 | `PSQL "select id, to_char(created_at AT TIME ZONE 'Asia/Shanghai','YYYY-MM-DD HH24:MI') from apps order by created_at desc limit 5"`；改用最新应用重跑，或把 grep 换成带应用名的精确上下文匹配 |
| 第 4 步 `web date` 是 UTC | 镜像未重新构建（旧镜像无 `tzdata`） | `docker compose images \| grep web` 看构建时间；`docker compose up -d --build web` 后再看 `date`（页面时间不受影响） |

### R-05 四项联合冒烟（一条脚本跑完）【汇总】

**覆盖维度**：用一条脚本把上面 4 个修复点一次性验完，输出 PASS / FAIL / SKIP 与通过数，供改动后快速回归。

**前置条件**
- `cd ~/atomlet`。
- **建议用 R-03 生成的那个应用来跑**（它有 `min>0` 的金额字段，C4 才能实测而不是 SKIP）；其他应用也能跑，C4 会降级为 SKIP。
- 已执行 §3 公共准备。

**执行步骤**

把下面整段存成 `~/atomlet/r05.sh`（或直接整段粘贴进终端）：

```bash
cd ~/atomlet
LOCAL=http://127.0.0.1:3000
PSQL() { docker compose exec -T db psql -U atomlet -d atomlet -tAc "$1"; }

APP_ID=${1:-$(PSQL "select id from apps order by created_at desc limit 1")}
if [ -z "$APP_ID" ]; then echo "FAIL: 库里没有应用，先生成一个"; exit 1; fi
echo "APP_ID=$APP_ID"

PASS=0; FAIL=0; SKIP=0; TOTAL=0
ok()   { TOTAL=$((TOTAL+1)); PASS=$((PASS+1)); echo "PASS  $1"; }
bad()  { TOTAL=$((TOTAL+1)); FAIL=$((FAIL+1)); echo "FAIL  $1 <- $2"; }
skp()  { TOTAL=$((TOTAL+1)); SKIP=$((SKIP+1)); echo "SKIP  $1 <- $2"; }

# C1 对话历史已落库（缺陷 1）
T=$(PSQL "select count(*) from pg_tables where schemaname='public' and tablename='messages'")
N=$(PSQL "select count(*) from messages where app_id='$APP_ID'")
if [ "$T" = "1" ] && [ "${N:-0}" -ge 2 ]; then
  ok "C1 messages 表存在，消息 $N 条"
else
  bad "C1 对话历史未落库" "table=$T count=$N"
fi

# C2 主题作用到 DOM（缺陷 2）
THEME=$(PSQL "select theme from apps where id='$APP_ID'")
case "$THEME" in
  cool) BRAND='#0E7490' ;;
  warm) BRAND='#B4530A' ;;
  *)    BRAND='#4F46E5' ;;
esac
curl -s "$LOCAL/apps/$APP_ID" > /tmp/r05_app.html
if grep -q "data-theme=\"$THEME\"" /tmp/r05_app.html && grep -q -- "$BRAND" /tmp/r05_app.html; then
  ok "C2 data-theme=$THEME 且出现 $BRAND"
else
  bad "C2 主题没作用到 DOM" "theme=$THEME brand=$BRAND"
fi

# C3 时间按北京时间渲染（缺陷 4）
EXP=$(PSQL "select to_char(created_at AT TIME ZONE 'Asia/Shanghai','YYYY-MM-DD HH24:MI') from apps where id='$APP_ID'")
UTC=$(PSQL "select to_char(created_at AT TIME ZONE 'UTC','YYYY-MM-DD HH24:MI') from apps where id='$APP_ID'")
curl -s "$LOCAL/" > /tmp/r05_home.html
if [ -z "$EXP" ]; then
  skp "C3 时间" "取不到 created_at"
elif grep -q "$EXP" /tmp/r05_home.html && ! grep -q "$UTC" /tmp/r05_home.html; then
  ok "C3 首页时间=$EXP（北京时间）"
else
  bad "C3 时间不是北京时间" "期望 $EXP / UTC=$UTC"
fi

# C4 金额下限（缺陷 3）
MKEY=$(PSQL "select f->>'key' from app_versions v, jsonb_array_elements(v.spec->'entities'->0->'fields') f where v.app_id='$APP_ID' and v.version=(select current_version from apps where id='$APP_ID') and f->>'type'='number' and (f->>'min')::numeric > 0 limit 1")
if [ -z "$MKEY" ]; then
  skp "C4 金额下限" "该应用没有 min>0 的数字字段"
else
  CODE=$(curl -s -o /tmp/r05_zero.json -w '%{http_code}' -X POST "$LOCAL/api/apps/$APP_ID/records" -H 'Content-Type: application/json' -d "{\"payload\":{\"$MKEY\":0}}")
  if [ "$CODE" = "422" ] && grep -q '必须大于' /tmp/r05_zero.json; then
    ok "C4 金额 0 被 422 拦下"
  else
    bad "C4 金额 0 未被拦" "code=$CODE body=$(head -c 120 /tmp/r05_zero.json)"
  fi
fi

echo "----"
echo "总计 $TOTAL 项：PASS=$PASS FAIL=$FAIL SKIP=$SKIP"
if [ "$FAIL" -eq 0 ]; then echo "结论：通过（FAIL=0）"; else echo "结论：不通过"; fi
```

运行：

```bash
bash ~/atomlet/r05.sh
```

也可以指定应用：

```bash
bash ~/atomlet/r05.sh 3f2b1a9c-1111-2222-3333-444455556666   # 把这里换成你的应用 ID
```

**期望输出**（对着 R-03 生成的应用跑）

```
APP_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
PASS  C1 messages 表存在，消息 2 条
PASS  C2 data-theme=cool 且出现 #0E7490
PASS  C3 首页时间=2026-10-26 14:03（北京时间）
PASS  C4 金额 0 被 422 拦下
----
总计 4 项：PASS=4 FAIL=0 SKIP=0
结论：通过（FAIL=0）
```

- 4 项检查里，`PASS` 数 = `4`、`FAIL` = `0` 是验收要求。
- 对着**没有金额约束**的应用跑，C4 会输出 `SKIP`（`总计 4 项：PASS=3 FAIL=0 SKIP=1`），这是脚本设计的降级，不是失败；要验 C4 请改用 R-03 的应用。
- C2 的 `THEME` 与 `BRAND` 是联动映射的（`cool→#0E7490`、`warm→#B4530A`、`neutral→#4F46E5`），所以应用是中性色时这条也应当 PASS——它验的是「HTML 里的色值与库里主题一致」，不要求主题必须是 cool。

**判定标准**

脚本输出 `FAIL=0` 且 `PASS=4`，即为通过。`FAIL>0` 时按对应编号回到 R-01 ~ R-04 查具体步骤；只有 `SKIP` 而没有 `FAIL` 时，补一个满足条件的应用重跑。

**失败排查**

| 现象 | 原因 | 修复命令 |
|---|---|---|
| `C1` FAIL 且 `table=` 输出空 | `docker compose exec` 在脚本里没分配 TTY，或 DB 容器没起 | 确认脚本里 `PSQL()` 带 `-T`；`docker compose ps` 看 `atomlet-db` 是否 healthy |
| `C2` FAIL 且 `theme=` 输出空 | `APP_ID` 取到的是空值（库里没应用），或应用被删 | `PSQL "select count(*) from apps"`；先生成一个应用再跑，或显式传入应用 ID |
| `C4` FAIL 且 `code=201` | 该应用的数字字段没有 `min`，脚本却找到了 `MKEY`（旧数据里手动改过 min） | `PSQL "select f->>'key',f->>'min' from app_versions v, jsonb_array_elements(v.spec->'entities'->0->'fields') f where v.app_id='$APP_ID' and v.version=(select current_version from apps where id='$APP_ID') and f->>'type'='number'"`；按 R-03 重新生成应用后重跑 |

## 7. 覆盖面边界（如实记录，别当成已验）

1. **表单端拦截只能人工验。** 仓库里没有 E2E 框架（无 Playwright / Cypress），R-03 第 5 步的「填 0 不发请求」只能靠 DevTools 的 Network 面板用眼睛确认，没有自动化断言。若以后接入 E2E，这条应转成自动化用例。
2. **`applyConstraintHints` 只覆盖特定字段名。** 它只给标签命中 `金额/费用/价格/成本/工资`（下限 0.01）或 `数量/件数/人数/次数`（下限 1）的 `number` 字段补 `min`，且要求 prompt 命中 `大于 0/不能为 0/必须为正/至少 1/不为 0`。模型若把字段命名成「报销额度」「支出额」这类不含关键词的标签，下限不会自动补——这是实现的覆盖面边界，不是本轮 4 个修复的回归目标。R-03 用「费用金额」措辞可稳定命中。
3. **对话历史只渲染最近 60 条。** `listMessages(appId, 60)` 限流，超过 60 条后页面只显示最近 60 条，旧的仍在库里。用例不覆盖 60+ 场景；若评审问「历史会不会无限增长撑爆页面」，答案是会增长、但页面有上限。
4. **容器 `date` 不作为判定项。** 见 §2 第 ③ 条：页面时间正确性与镜像是否带 `tzdata` 无关，`date` 只是附加证据。
