# 09 部署与运维方案

> 项目：Atomlet（小原子）｜上游：06 架构（单实例 + 外置 Postgres）、08 数据模型（DDL 与备份对象）
> 目标：6 小时内把系统放到公网，且能回答"挂了怎么办、数据丢了怎么办、成本涨了怎么办"。

## 1. 环境清单

| 环境 | 用途 | 形态 | 数据库 | 访问方式 | 备注 |
|---|---|---|---|---|---|
| 本地 dev | 编码与联调 | `pnpm dev`（3000） | Docker Postgres 16（5432） | `http://localhost:3000` | HMR，可连远程 LLM |
| 预发 staging | 上线前冒烟 | Docker Compose 单机 | 同容器内 Postgres | `http://<EIP>:3000` | 与生产同镜像，用于验证迁移脚本 |
| 生产 prod | 演示与交付 | Docker 单容器 + 外置 Postgres | 阿里云 RDS 或同机 Postgres | `http://<EIP>:3000`（备案后切域名） | 只跑 `node server.js`，不带源码 |

三个环境用**同一份 Dockerfile**，差异只在 `.env`。这是刻意的：预发与生产镜像一致，才能让"预发通过"有意义。

## 2. 部署架构

```
              Internet
                 │  http :3000（无域名阶段） / https :443（备案后）
        ┌────────▼─────────┐
        │  Nginx（可选反代）│  proxy_buffering off;  ← SSE 必需
        └────────┬─────────┘
        ┌────────▼──────────────────────────────────┐
        │ Docker: atomlet-web（node server.js, :3000）│
        │   RSC / Route Handlers / SSE 长连接         │
        └────────┬──────────────────────────────────┘
        ┌────────▼──────────────────────────────────┐
        │ Postgres 16（RDS 或同机容器，卷 pgdata）     │
        └───────────────────────────────────────────┘
```

### 为什么不用 Vercel + SQLite

| 维度 | Vercel + SQLite | 阿里云 ECS + Docker + Postgres（选用） |
|---|---|---|
| 文件系统 | **只读**，`/tmp` 之外不可写，SQLite 无处落盘 | 可挂卷，任意写 |
| 持久化 | serverless 实例随时销毁，本地文件不跨实例 | 命名卷 / RDS，跨重启保留 |
| SSE 时长 | 函数执行有最大时长，50s 生成会被掐断 | 长连接不受限，只要 Nginx 不缓冲 |
| 连接数 | 每个函数实例独立连接，Postgres 易被打满 | 单实例固定连接池，可控 |
| 成本 | 免费档够用 | ≈ ¥90/月 |

> 若确实需要 Vercel（例如想蹭免费额度），必须换 Neon 这类外部 Postgres，且把生成改成"轮询任务状态"而非 SSE —— 这是备选方案，不是默认路径。

## 3. Dockerfile（可直接用）

```dockerfile
# next.config.mjs 必须设置 output: 'standalone'
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NEXT_TELEMETRY_DISABLED=1
RUN corepack enable && pnpm build

FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production PORT=3000 HOSTNAME=0.0.0.0
RUN addgroup -g 1001 nodejs && adduser -u 1001 -G nodejs -s /bin/sh -D nextjs
COPY --from=builder /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
USER nextjs
EXPOSE 3000
CMD ["node", "server.js"]
```

```js
// next.config.mjs
export default { output: 'standalone', experimental: { serverActions: { bodySizeLimit: '2mb' } } };
```

## 4. docker-compose.yml（可直接用）

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: atomlet
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?POSTGRES_PASSWORD is required}
      POSTGRES_DB: atomlet
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U atomlet -d atomlet"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

  web:
    build: .
    env_file: .env
    ports: ["3000:3000"]
    depends_on:
      db: { condition: service_healthy }
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:3000/api/healthz"]
      interval: 15s
      retries: 5
    restart: unless-stopped

volumes:
  pgdata:
```

Nginx（备案后用）关键三行：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Connection '';
    proxy_buffering off;          # SSE 必需，否则前端一次性收到全部内容
    proxy_cache off;
    proxy_read_timeout 300s;      # 覆盖 90s 生成超时
    chunked_transfer_encoding on;
}
```

## 6. 数据库初始化与迁移策略

| 阶段 | 命令 | 说明 |
|---|---|---|
| 本地首次 | `docker compose up -d db` → `pnpm drizzle-kit push` | push 直接对齐 schema，适合快速迭代 |
| 有变更 | `pnpm drizzle-kit generate` → 人工 review `drizzle/*.sql` | 生成 SQL 后必须读一遍，防止 drop 列 |
| 预发/生产 | `pnpm drizzle-kit migrate` | 只走已提交的迁移文件，不 push |
| 种子数据 | `pnpm tsx scripts/seed.ts` | demo 账号 + 2 个预置应用（巡检 / 报修），演示兜底用 |
| 校验 | `pnpm tsx scripts/seed.ts --verify` | 断言 7 张表存在、demo 应用 spec 可加载 |

> **时间盒取舍**：MVP 阶段开发用 `push`，上线前一次性 `generate` 出 `0000_init.sql` 并在预发跑一遍 `migrate`。不做自动迁移（容器启动时 migrate 会让多实例并发迁移，单实例也容易在 DB 未就绪时失败）。迁移是**部署 checklist 里的一个显式步骤**，不是自动行为。

## 7. 上线步骤 Checklist

1. 确认 `.env` 12 个变量齐备，`DATABASE_URL` 在服务器上 `psql` 可连（`psql "$DATABASE_URL" -c 'select 1'`）。
2. `docker compose build` 成功，镜像大小 < 300 MB。
3. `docker compose up -d db`，等 healthcheck 变 `healthy`。
4. `pnpm drizzle-kit migrate` 执行成功（预发先跑，生产后跑）。
5. `pnpm tsx scripts/seed.ts` 写入 demo 账号与 2 个预置应用。
6. `docker compose up -d web`，`curl -s http://127.0.0.1:3000/api/healthz` 返回 `{"ok":true,"db":"up"}`。
7. 安全组放行 3000（或 80/443），从**外部网络**访问 `http://<EIP>:3000` 打开首页。
8. 冒烟：登录 → 用门店巡检 CSV 生成 → 录入 1 条记录 → 刷新仍在 → 创建分享链接并在无痕窗口打开填报 → 提交成功。
9. **域名备案提示**：国内 ECS 绑域名需 ICP 备案（通常 7–20 个工作日），48 小时内大概率来不及。**直接用 `IP:3000` 访问是本次交付的默认路径**，`PUBLIC_BASE_URL` 同步改成 IP，否则分享链接会指向不存在的域名。如已有备案域名，则在 Nginx 里加 `server_name` 并申请免费证书。
10. 记录并归档：镜像 tag（`atomlet:2025-10-25`）、迁移版本、`PUBLIC_BASE_URL`、冒烟结果截图路径。

## 8. 可观测性

**结构化日志**（stdout 单行 JSON，Docker `json-file` driver 收集）：

| 字段 | 示例 | 用途 |
|---|---|---|
| `ts` | `2025-10-25T09:01:22.431Z` | 排序 |
| `level` | `info` / `warn` / `error` | 过滤 |
| `requestId` | `req_8f2a…` | 全链路串联，同时回给前端用于报障 |
| `route` | `POST /api/apps/generate` | 聚合 |
| `userId` / `appId` / `runId` | `u_1` / `a_9` / `r_7` | 归因 |
| `latencyMs` | `24110` | 性能 |
| `status` / `code` | `200` / `GENERATE_FAILED` | 错误率 |
| `tokensIn` / `tokensOut` / `costCny` | `22000` / `9000` / `0.0400` | 成本 |

**埋点（落 `gen_runs` / `gen_steps`，不引入第三方 APM）**：

| 指标 | 口径 | 告警阈值（人工看板即可） |
|---|---|---|
| 生成成功率 | `status IN (succeeded, degraded)` / 总 run（按小时） | < 80% 需看 prompt |
| 降级率 | `status='degraded'` / 总 run | > 15% 说明校验过严或模型不稳 |
| 生成 P50 / P95 耗时 | `latency_ms` 分位 | P95 > 60s 需查 provider |
| 平均重试次数 / 单次成本 | `avg(attempt)` / `avg(cost_cny)` | > 1.0 说明首轮质量差；偏离 ¥0.04 一个数量级要查 provider 配置 |
| 公开填报失败率 | `gen_runs` 之外单独计数（`source='public'` 的 422 比例） | > 20% 说明 spec 校验与表单不一致 |

**错误上报**：MVP 不接 Sentry，`error` 级日志 + `gen_runs.error` 已足够；前端捕获未处理异常后 `console.error` 附带 `requestId`，用户报障时报这个 id 即可定位。若后续接入 Sentry，只需在 `app/layout.tsx` 加一个 client 侧的 `Sentry.init`，服务端在错误中间件里 `captureException`。

## 9. 性能与容量预估

| 指标 | 预估 | 依据 |
|---|---|---|
| 单实例进程数 | 1（Node 单进程） | Next standalone，不用 PM2 cluster（Postgres 有连接池，单进程足够） |
| 页面渲染 P95 | < 300 ms | 单个 stats 页聚合 < 500 ms（`app_id` 索引 + GIN） |
| SSE 长连接并发 | ≈ 100 | 每连接仅占内存，无额外线程；受 Nginx `worker_connections` 与文件描述符限制 |
| 生成并发 / 排队 | 3（信号量）；超出进入 `queued` 并挂起 SSE | 模型侧限流 + 单次 20–40 MB 内存；队列无上限但 run 有 90s 超时，天然限流 |
| DB 连接池 | max 10 / instance | 2C4G 的 RDS 基础版足够；池满时新请求排队而非报错 |
| 记录查询 / 单应用容量 | 50 万行内 P95 < 200 ms；建议上限 50 万行 | GIN + `(app_id, entity, created_at)` 复合索引；超此触发 ADR-01 演进 |
| 磁盘 | 40 GB ESSD，100 应用 × 1 万行 ≈ 500 MB | 余量充足 |

## 10. 备份与回滚

### 10.1 数据备份与恢复（数据层）

```bash
# 每日 03:00 全量备份，保留 7 天
0 3 * * * docker exec atomlet-db pg_dump -U atomlet -Fc atomlet \
  > /backup/atomlet-$(date +\%F).dump && find /backup -name 'atomlet-*.dump' -mtime +7 -delete
```

| 项 | 值 |
|---|---|
| 备份对象 | 全库（7 张表，含 `app_records` 业务数据与 `app_versions` 历史） |
| 频率 / 保留 | 每日 1 次全量 + 上线前手动 1 次；保留 7 天 |
| RPO / RTO | RPO ≤ 24 小时（演示系统，非交易系统）；RTO ≈ 10 分钟（`pg_restore` 到新库 + 改 `DATABASE_URL` + 重启容器） |
| 恢复演练 | 上线前必须 `pg_restore` 到临时库并 `select count(*)` 对账；不演练的备份视为不存在 |

```bash
# 恢复
docker exec -i atomlet-db pg_restore -U atomlet -d atomlet_restore --clean --if-exists < /backup/atomlet-2025-10-24.dump
```

### 10.2 应用版本回滚（应用层，两件事之二）

| 场景 | 手段 | 命令/操作 | 影响面 |
|---|---|---|---|
| 用户把 spec 改坏了 | **spec 版本回滚** | `POST /api/apps/:id/versions/:vid/rollback` | 只影响一个应用，数据（`app_records`）不受影响 |
| 新代码有 bug | **镜像回滚** | `docker compose down web && docker tag atomlet:prev atomlet:current && docker compose up -d web` | 影响全站，DB schema 不回退 |
| 迁移写错了 | 先镜像回滚，**再**写补偿迁移 | 不做数据库向下迁移（不可逆风险高），用新迁移抵消 | 需人工确认 |

> 原则：**数据库只向前迁移**。代码可回滚，schema 不回头；出错时用"新迁移修正"而不是"还原旧迁移"。

## 11. 运维常见故障 5 例

### 例 1：SSE 被反向代理缓冲，前端一次性收到全部内容

**现象**：进度条不动，30 秒后所有事件同时出现。
**定位**：`curl -N http://host/api/apps/generate -d ...` 直连容器有分块输出，过 Nginx 没有 → 反代缓冲。
**处置**：Nginx 加 `proxy_buffering off; proxy_cache off; proxy_set_header Connection '';`；应用侧响应头补 `Cache-Control: no-cache, no-transform` 与 `X-Accel-Buffering: no`。
**预防**：`/api/healthz` 增加一个 `/api/healthz/stream` 探针，部署 checklist 第 8 步用它验证流式。

### 例 2：生成超时（504 GENERATE_TIMEOUT）

**现象**：run 停在 `BUILDING`，90s 后被判超时。
**定位**：查 `gen_steps` 最后一条 `status=running` 的 agent；查 `latency_ms` 是否集中在 builder。
**处置**：① 换更快的 provider（DeepSeek 优先）；② 缩短 prompt 的 few-shot；③ 检查是否触发了 repair 循环（`attempt` 接近 3）。**不要**直接调大 `GEN_TIMEOUT_MS`，那只是把失败推后。
**预防**：builder 输出截断阈值 4000 tokens，超过则提前终止并按 L2 局部修复收口。

### 例 3：DB 连接池耗尽

**现象**：`timeout exceeded when trying to connect`，`/api/healthz` 的 `db` 变 `down`。
**定位**：`SELECT count(*) FROM pg_stat_activity WHERE datname='atomlet';` 对比 `max_connections`。
**处置**：① 确认没有在 handler 里泄漏客户端（每个请求必须复用单例 Pool）；② `max=10` 且 `idleTimeoutMillis=30000`；③ 临时重启容器恢复，再改代码。
**预防**：SSE handler 在流结束后必须释放连接（不持有事务），长连接期间不留开着的事务。

### 例 4：上传大文件导致 413 或内存暴涨

**现象**：上传 8 MB CSV 返回 413，或 Node 进程 RSS 飙升。
**定位**：`serverActions.bodySizeLimit` / 自建 handler 的 `req.arrayBuffer()` 全量读入。
**处置**：前端先行限制（2 MB / 5000 行），后端流式按行读取只解析前 200 行做类型推断，全量数据不落库（只用于推断）。
**预防**：`PAYLOAD_TOO_LARGE` 错误码 + 前端文案"请只保留表头与前 200 行样例"。

### 例 5：分享 token 泄露（被外部爬取后批量写入）

**现象**：某应用的记录数异常增长，`source='public'` 占比突增。
**定位**：`SELECT app_id, count(*) FROM app_records WHERE source='public' GROUP BY 1 ORDER BY 2 DESC;` 再看 `share_links` 对应 token 的 `expires_at`。
**处置**：① 立刻 `DELETE /api/apps/:id/share-links/:lid`（写 `revoked_at`，下次请求即失效）；② 重新生成 token；③ 按 `created_at` 区间 + `source` 删异常记录。
**预防**：token 默认 7 天过期；公开写接口按 IP + token 双维度限流（10 次/分）；写入日志必带 `requestId` 与 IP 便于事后追。

## 12. 成本与容量小结

ECS 2C4G ¥90/月 + Postgres（同机容器 ¥0 / RDS 基础版 ≈ ¥60/月）+ 模型调用（≈ ¥0.04/次，100 应用/月 ≈ ¥16 用 DeepSeek ～ ¥565 用 Claude）+ 无对象存储（`url` 字段只存外部链接）= **演示期 ≈ ¥90–150/月，100 应用/月 ≈ ¥106–715/月**。

与 01 文档第 3 节一致。成本不构成约束，因此**不引入计费与配额系统**（明确在范围外）。
