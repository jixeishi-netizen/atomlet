# 06 总体架构设计

> 项目：Atomlet（小原子）｜对应交付物：可运行的多智能体应用生成器
> 上游依赖：01 可行性分析（方案 C 已定）｜下游文档：07 生成链路、08 数据模型与接口、09 部署运维

## 1. 设计目标与约束

### 1.1 目标（按优先级排序）

| # | 目标 | 可度量标准 |
|---|---|---|
| G1 | 一句话/一张表 → 一个可用的内部系统 | 从提交需求到页面可交互，端到端 P50 ≤ 25s，P95 ≤ 50s |
| G2 | 生成的系统能真实录入与查询数据 | 刷新后数据仍在；跨设备用同一 URL 可见同一份数据 |
| G3 | 修改是"最小变更"，不是重生成 | 一次增量修改只产生一条 JSON Patch，diff 行数 ≤ 20 行 |
| G4 | 生成失败可解释、可恢复 | 每次失败都有 `gen_runs.status=failed` + `error` + 可点重试 |
| G5 | 单个开发者 6 小时内能上线 | P0 总工时 ≤ 6.0h（见 01 文档第 4 节） |

### 1.2 硬约束

| 类型 | 约束 | 架构上的应对 |
|---|---|---|
| 时间 | 有效开发 6–8 小时，单人 | 不自研运行时、不自研编辑器、不自研消息队列；能用库就用库 |
| 人力 | 单开发者 | 单仓单进程，前后端同仓（Next Route Handlers），不做微服务 |
| 部署 | 一台 2C4G ECS，可能无域名 | 单 Docker 容器 + 外置 Postgres；监听 3000，反代可选 |
| 安全 | 不执行模型生成的任意代码 | 模型只输出 JSON，前端只渲染白名单组件；无 `eval`、无 iframe 执行 |
| 成本 | 模型成本可忽略，但不能失控 | provider 抽象 + 每 run 记 tokens/cost，超阈值即可切换更便宜的模型 |

### 2.2 依赖方向（单向，禁止回指）

| 从 | 到 | 允许 | 说明 |
|---|---|---|---|
| L1 接入层 | L2 应用层 | 仅通过 HTTP | 页面不直接 import 数据层，也不 import 智能体层 |
| L2 应用层 | L3 编排层 | 允许 | 但只能调 `runGeneration()` / `runPatch()` 这类门面函数 |
| L2 应用层 | L5 数据层 | 允许 | 通过 `src/db/queries/*` 封装，不在 handler 里写裸 SQL |
| L3 编排层 | L5 数据层 | **禁止** | 编排层不落库；产物通过返回值交回应用层写库（便于单测） |
| L1 接入层 | L4 渲染层 | 允许 | 渲染层是纯函数组件库 |
| L4 渲染层 | L5 数据层 | **禁止** | 渲染层通过 props 拿数据，不自己查询 |

> 关键收益：**L3 与 L5 解耦**后，生成链路可以在无数据库的情况下用 fixture 跑 golden set，这让"生成质量评估"变成一个可重复执行的脚本，而不是手工点页面。

## 4. 关键数据流：生成时序

以"上传门店巡检表 → 生成应用"为例。每一步标注输入、输出与失败分支。

| 步 | 阶段 | 输入 | 输出 | 失败分支 |
|---|---|---|---|---|
| 0 | 客户端提交 | 文件 `< 2MB` 或文本 `< 4KB` | `POST /api/apps/generate` | 超限 → 413 `PAYLOAD_TOO_LARGE` |
| 1 | 鉴权 + 建 run | session | `gen_runs` 插入 `status=queued`，返回 `runId` | 未登录 → 401 |
| 2 | **parser** | 原始 CSV 前 200 行 | `{ columns: [{name, sample, inferredType, enumValues?}] }` | 无表头/全空 → 422 `PARSE_FAILED`，直接结束不消耗模型 |
| 3 | **planner** | 需求文本 + 列推断 + 组件能力清单 | `Blueprint = { entities[], pages[], actions[] }`（不含字段细节） | 模型超时 → 重试 1 次；仍失败 → 502 `GENERATE_FAILED` |
| 4 | **builder** | Blueprint + 完整 JSON Schema（作为 tool 定义） | 完整 `AppSpec` | JSON 解析失败 → 带解析错误回灌重试 1 次 |
| 5 | **critic** | 完整 AppSpec | `issues: [{level: error\|warn, path, message}]` | critic 自身失败 → 降级为纯 zod 校验，`status=degraded` |
| 6 | 判定 | issues | `error` 数 = 0 → 进入 7；否则进入 6a | — |
| 6a | **repair** | spec + error 级 issues | 修复后的 spec | 重试 3 次仍失败 → 三级兜底：回退最接近模板 + 明确告知用户"已使用模板，原因是…" |
| 7 | 落库（事务） | 合法 spec | `apps` + `app_versions(v1)` + 更新 `gen_runs.status=succeeded` | 事务失败 → 502，不留半成品 |
| 8 | 客户端 | SSE `event: done {appId, versionNo}` | 跳转 `/apps/[id]` | 连接中断 → 前端用 `runId` 补偿查询 `GET /api/gen-runs/:id` |

> SSE 期间服务端逐条推送 `event: step`（`{agent, status, summary}`）与 `event: token`（Builder 的增量文本），末条 `event: done` 或 `event: error`。前端不解析中间态 JSON，只用它做进度展示——避免把流式协议变成第二个契约面。

## 6. 技术选型表

| 层 | 选型 | 版本 | 为什么不选替代品 |
|---|---|---|---|
| 框架 | Next.js App Router | 14.x | 不选 Vite+Express：需要同仓 SSR + API + 未来 RSC 数据直取，双仓会多一套构建与部署；不选 Remix：社区样例与 Drizzle 集成资料少于 Next |
| 语言 | TypeScript strict | 5.x | 不选 JS：AppSpec 的类型是架构核心资产，必须靠类型守住渲染器与 schema 的一致性 |
| 样式 | Tailwind CSS | 3.4 | 不选 CSS-in-JS：多一层运行时与构建配置；不引 UI 组件库（Antd/MUI）：需要定制 6 个数据视图，组件库反而增加适配成本。shadcn/ui 只借组件命名与 API 形状、**不执行 `init` 装依赖**（见 14 §2 开头），保留后续一对一平替的可能 |
| 数据访问 | Drizzle ORM | 0.30+ | 不选 Prisma：Prisma 需要 generate 步骤、二进制引擎让 Docker 镜像变大；Drizzle 是 TS 原生、SQL-like，JSONB 的 `->>` 表达式可直写，且 `drizzle-kit push` 适合时间盒 |
| 数据库 | Postgres 16 | 16 | 不选 SQLite：需要并发写 + JSONB GIN 索引 + 后续 DDL 演进；不选 MongoDB：需要事务与关系约束（apps↔versions↔records） |
| 校验 | zod | 3.x | 不选 Joi/Yup：zod 从 schema 直接推 TS 类型，AppSpec 的类型与运行时校验共用一份定义；且 `zod-to-json-schema` 能把同一份定义转成模型用的 JSON Schema |
| 模型调用 | 自建 provider 抽象 | — | 不选 LangChain：抽象层过重、调试黑盒、SSE 透传麻烦；本项目只需要"三次结构化调用 + 一次 repair"，200 行足够 |
| 结构化输出 | JSON Schema + 一次修复重试 | — | 不选 function calling 强依赖：不同 provider 支持度不一，统一走"提示词内联 schema + 解析失败回灌"更稳 |
| 流式 | 原生 ReadableStream SSE | — | 不选 WebSocket：单向推送用 SSE 足够，WS 需要额外服务端与心跳；不选 Vercel AI SDK：绑定其消息协议，反而多一层要理解的契约 |
| 任务状态 | Postgres `gen_runs`/`gen_steps` | — | 不选 Redis/BullMQ：多一个组件要部署，且任务状态需要可查询（面试官会问"生成失败了怎么查"），落库天然可查 |
| 鉴权 | 自建 cookie session（demo 账号）+ share token | — | 不选 NextAuth：本项目只有一种登录方式，NextAuth 的 provider 矩阵是净负担；不选 JWT 无状态：需要"撤销分享链接"能力，必须有服务端状态 |
| 部署 | Docker 单容器 + 外置 Postgres | — | 不选 Vercel serverless：文件系统只读、无持久化、SSE 有执行时长限制；不选 K8s：单实例不需要编排 |

## 7. 架构决策记录（ADR）

### ADR-01 数据持久化：统一 `app_records` 表 + JSONB payload，不做运行时 DDL

- **状态**：已接受
- **背景**：逻辑上"一个应用一套数据模型"（每个 AppSpec 的 entities 不同）。物理上必须在两种方案里选：
  - (a) 生成时执行 `CREATE TABLE app_<id>_<entity>`，每个应用一套真表；
  - (b) 所有应用共用 `app_records`，业务字段放 JSONB，用 `app_id` 隔离。
- **决策**：MVP 采用 **(b)**。所有记录写入 `app_records(app_id, entity, payload jsonb)`，写入前按该应用当前版本 spec 做**字段级校验**（必填/类型/枚举/唯一），查询用 `payload->>'field'` + GIN 索引。
- **理由**（三条，缺一不可）：
  1. **运行时 DDL 有注入与迁移不可控风险**。表名/列名来自模型输出，必须做标识符白名单与转义；一旦漏了就是 SQL 注入面。而 DDL 无法回滚到"上一个版本的 schema"，改字段类型需要迁移脚本，模型不可能产出可靠迁移。
  2. **多租户管理成本高**。每个应用 N 张表，100 个应用就是数百张表，`pg_class` 膨胀、连接池与权限管理、备份恢复粒度都会变复杂。
  3. **6–8h 时间盒不允许做迁移器**。DDL 生成器 + 迁移器 + 数据回填至少 2.5h，且是一次性投入、演示时看不出差别。
- **后果**：
  - 正面：一次建表永久可用；schema 变更零迁移（payload 天然松散）；备份/回滚粒度是行级。
  - 负面：**失去复杂索引与约束能力**（唯一约束靠应用层 + 部分唯一索引实现）；跨应用聚合需要 `app_id` 过滤，全表扫描风险高；大字段值查询依赖 GIN，范围查询与排序在 50 万行以上会退化。
  - 已知代价：唯一字段校验用"先查后写"存在并发窗口（README 中如实记录，P2 用 `CREATE UNIQUE INDEX ... ((payload->>'x')) WHERE app_id=... ` 补齐）。
- **演进路径（P2，不在 MVP）**：预留 `src/db/ddl.ts` 接口 —— `generateDDL(spec): string` 产出 `CREATE TABLE` 模板，`migrate(appId, fromSpec, toSpec): Migration[]`。触发条件：**单应用记录数 > 50 万** 或 **需要复杂/联合索引**。届时按应用"升舱"：把热点应用从 `app_records` 迁到专属表，`app_records` 保留为长尾应用的默认承载。

### ADR-02 模型只输出 AppSpec（JSON），不输出 HTML

- **状态**：已接受
- **背景**：直出 HTML 演示效果最好，但无法做增量修改、无法校验、无法版本化。见 01 文档第 5 节对比。
- **决策**：模型输出受 JSON Schema 约束的 AppSpec；前端用固定 6 个页面组件 + 9 种字段控件渲染。
- **后果**：表达力锁死在白名单内；换来 100% 可校验、可 patch、可回滚。渲染器必须对越界配置降级而非白屏。

### ADR-03 生成链路用"编译式"三段而非"多智能体自由对话"

- **状态**：已接受
- **背景**：MetaGPT 式的多智能体自由协作在开放任务上强，但在"必须产出合法 JSON"的约束任务上，自由对话会引入不可控的发散。
- **决策**：Planner / Builder / Critic 三段**串行且契约固定**：每段有明确输入结构、输出结构、失败处理。Critic 不是"讨论者"，而是"校验器的语义补充"，输出结构化问题单。
- **后果**：调试可定位（哪一段坏了看 `gen_steps`）；代价是无法处理"Planner 拆错了整个方案要重来"的情况——此时回退到模板兜底，不试图让智能体互相说服。

### ADR-04 增量修改用 JSON Patch 而非重生成

- **状态**：已接受
- **背景**：重生成成本低（¥0.04），但会丢掉用户已有数据绑定、让 diff 不可读、无法回滚到"只改了一处"的状态。
- **决策**：模型输出 RFC 6902 子集（`add`/`replace`/`remove`/`move` 四操作），服务端做 path 白名单 + apply 后重新 zod 校验，落地为新版本快照。
- **后果**：patch 路径不存在时**整条丢弃并提示用户重述**，不做"整页重生"兜底 —— 否则会出现"我只想改个标题结果页面全变了"的失控感。这是刻意的产品取舍。

### ADR-05 单进程内生成排队，不引入消息队列

- **状态**：已接受
- **背景**：生成是 20–50s 的长任务，需要限制并发（模型限流 + 内存占用）。
- **决策**：进程内信号量（`maxConcurrent = 3`）+ `gen_runs.status=queued` 落库。SSE 连接挂起等待自己的 run 被调度。超时 90s 强制失败并写 `error`。
- **后果**：单实例够用；**多实例部署会失效**（各自计数），需改 DB advisory lock —— 已记录为已知限制，部署文档只承诺单实例。

## 8. 可扩展性设计：三处扩展点

### 8.1 新增组件类型（如 calendar / gantt）

只需改三处，不动生成编排：

| 步骤 | 文件 | 改动 |
|---|---|---|
| 1 | `src/spec/schema.ts` | `pageType` 枚举加 `'calendar'`，并补该类型的 props schema（zod discriminated union） |
| 2 | `src/runtime/pages/CalendarPage.tsx` | 新建组件，props 类型从 zod 推导 |
| 3 | `src/runtime/registry.ts` | `pageRegistry.calendar = CalendarPage` |

同时更新 `prompts/v1.builder.ts` 里的"能力清单"（这是 prompt 的唯一事实来源），并跑 `scripts/golden-set.ts` 回归。

### 8.2 新增实体字段类型（如 file / address）

| 步骤 | 文件 | 改动 |
|---|---|---|
| 1 | `src/spec/schema.ts` | `fieldType` 枚举加值 + 该类型的额外约束（如 `maxSizeMB`） |
| 2 | `src/runtime/fields/AddressField.tsx` | 新建控件 |
| 3 | `src/runtime/registry.ts` | `fieldRegistry.address` |
| 4 | `src/db/queries/records.ts` | `coerceValue()` 加该类型的服务端校验分支 |

> 字段类型是**校验与渲染的唯一交叉点**，扩展时必须同时改这两处，漏一处会导致"能填不能存"或"能存不能显示"。这条约束写在 `registry.ts` 的注释里。

### 8.3 切换模型 provider

| 能力 | 接口 | 说明 |
|---|---|---|
| 注册 | `provider.ts` 的 `PROVIDERS: Record<string, Provider>` | 新增 `gemini.ts` 实现 `chat()` 即可 |
